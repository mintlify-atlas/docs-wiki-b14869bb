`MyCompanyName.MyProjectName.EntityFrameworkCore` is one of the two interchangeable persistence projects shipped by the application template. It contains the `DbContext`, the EF Core entity configurations for the bundled ABP modules, a design-time factory used by `dotnet ef`, and the `IMyProjectNameDbSchemaMigrator` implementation that the `DbMigrator` console invokes.

The template defaults to **SQL Server** (the csproj references `Volo.Abp.EntityFrameworkCore.SqlServer`). The same project is used for PostgreSQL, MySQL, Oracle and SQLite — only one `ProjectReference` and the `options.UseSqlServer()` call need to change.

## When to put code here

Add a file here when it is:

- An EF Core `IEntityTypeConfiguration<T>` or fluent-API mapping for one of your aggregate roots.
- A repository implementation that needs LINQ-to-Entities (`IEnumerable<Book> GetWithAuthorsAsync()`).
- A migration generated by `dotnet ef migrations add ...`.
- Extra property mapping registered via `ObjectExtensionManager` for module entities.

## Module class

```csharp
[DependsOn(
    typeof(MyProjectNameDomainModule),
    typeof(AbpIdentityEntityFrameworkCoreModule),
    typeof(AbpOpenIddictEntityFrameworkCoreModule),
    typeof(AbpPermissionManagementEntityFrameworkCoreModule),
    typeof(AbpSettingManagementEntityFrameworkCoreModule),
    typeof(AbpEntityFrameworkCoreSqlServerModule),
    typeof(AbpBackgroundJobsEntityFrameworkCoreModule),
    typeof(AbpAuditLoggingEntityFrameworkCoreModule),
    typeof(AbpTenantManagementEntityFrameworkCoreModule),
    typeof(AbpFeatureManagementEntityFrameworkCoreModule))]
public class MyProjectNameEntityFrameworkCoreModule : AbpModule
{
    public override void PreConfigureServices(ServiceConfigurationContext context)
    {
        MyProjectNameEfCoreEntityExtensionMappings.Configure();
    }

    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        context.Services.AddAbpDbContext<MyProjectNameDbContext>(options =>
        {
            options.AddDefaultRepositories(includeAllEntities: true);
        });

        Configure<AbpDbContextOptions>(options =>
        {
            options.UseSqlServer();
        });
    }
}
```

Highlights:

- **`AddDefaultRepositories(includeAllEntities: true)`** — creates generic `IRepository<TEntity, TKey>` registrations for every entity in `MyProjectNameDbContext`, including the ones inherited via `ReplaceDbContext`. Switch to `includeAllEntities: false` once you want only aggregate-root repositories (the [DDD best practice](https://docs.abp.io/en/abp/latest/Best-Practices/Entity-Framework-Core-Integration)).
- **`options.UseSqlServer()`** — the single API call you change to switch providers. The matching reference in the csproj also has to change.
- For SQLite, the template additionally configures `AbpUnitOfWorkDefaultOptions.TransactionBehavior = Disabled` because SQLite cannot wrap DDL in transactions.

## Key types

### MyProjectNameDbContext

```csharp
[ReplaceDbContext(typeof(IIdentityDbContext))]
[ReplaceDbContext(typeof(ITenantManagementDbContext))]
[ConnectionStringName("Default")]
public class MyProjectNameDbContext :
    AbpDbContext<MyProjectNameDbContext>,
    IIdentityDbContext,
    ITenantManagementDbContext
{
    public DbSet<IdentityUser> Users { get; set; }
    public DbSet<IdentityRole> Roles { get; set; }
    public DbSet<IdentityClaimType> ClaimTypes { get; set; }
    public DbSet<OrganizationUnit> OrganizationUnits { get; set; }
    public DbSet<IdentitySecurityLog> SecurityLogs { get; set; }
    public DbSet<IdentityLinkUser> LinkUsers { get; set; }
    public DbSet<IdentityUserDelegation> UserDelegations { get; set; }
    public DbSet<Tenant> Tenants { get; set; }
    public DbSet<TenantConnectionString> TenantConnectionStrings { get; set; }
    // ...
}
```

The two `[ReplaceDbContext]` attributes are the magic that lets you write a **single** EF Core context for the whole solution. Without them you would get separate `IdentityDbContext`, `TenantManagementDbContext`, etc. — and could not perform a JOIN across `Users` and `Tenants` directly. By replacing those interfaces the modules' repositories run against `MyProjectNameDbContext` at runtime.

`OnModelCreating` calls `builder.ConfigurePermissionManagement()` and friends so each module registers its own tables on the consolidated context:

```csharp
builder.ConfigurePermissionManagement();
builder.ConfigureSettingManagement();
builder.ConfigureBackgroundJobs();
builder.ConfigureAuditLogging();
builder.ConfigureIdentity();
builder.ConfigureOpenIddict();
builder.ConfigureFeatureManagement();
builder.ConfigureTenantManagement();
```

### MyProjectNameDbContextFactory

`IDesignTimeDbContextFactory<MyProjectNameDbContext>` implementation that lets `dotnet ef` commands work without booting the full application:

```csharp
public MyProjectNameDbContext CreateDbContext(string[] args)
{
    MyProjectNameEfCoreEntityExtensionMappings.Configure();
    var configuration = BuildConfiguration();
    var builder = new DbContextOptionsBuilder<MyProjectNameDbContext>()
        .UseSqlServer(configuration.GetConnectionString("Default"));
    return new MyProjectNameDbContext(builder.Options);
}

private static IConfigurationRoot BuildConfiguration()
{
    var builder = new ConfigurationBuilder()
        .SetBasePath(Path.Combine(Directory.GetCurrentDirectory(),
            "../MyCompanyName.MyProjectName.DbMigrator/"))
        .AddJsonFile("appsettings.json", optional: false);
    return builder.Build();
}
```

Note the **relative path** to `DbMigrator/appsettings.json` — the connection string used for migrations is the one the `DbMigrator` will run with, *not* the one in the API host's `appsettings.json`. This avoids creating two databases by accident when developers run `Add-Migration` and then the migrator.

### EntityFrameworkCoreMyProjectNameDbSchemaMigrator

Implements the database-agnostic interface from `Domain`:

```csharp
public async Task MigrateAsync()
{
    await _serviceProvider
        .GetRequiredService<MyProjectNameDbContext>()
        .Database
        .MigrateAsync();
}
```

The `DbContext` is resolved from `IServiceProvider` rather than constructor-injected so multi-tenant connection-string resolution kicks in correctly within `MyProjectNameDbMigrationService`.

### MyProjectNameEfCoreEntityExtensionMappings

Static `OneTimeRunner` block where you wire ABP's [Entity Extension](https://docs.abp.io/en/abp/latest/Customizing-Application-Modules-Extending-Entities) system to physical columns:

```csharp
ObjectExtensionManager.Instance
    .MapEfCoreProperty<IdentityUser, string>(
        "MyProperty",
        (entityBuilder, propertyBuilder) => { propertyBuilder.HasMaxLength(128); });
```

This call runs from both `PreConfigureServices` (at host startup) and `MyProjectNameDbContextFactory.CreateDbContext` (at `dotnet ef` time) so the migration generator sees the same model the runtime does.

## Switching the database provider

1. Replace the `Volo.Abp.EntityFrameworkCore.SqlServer` reference with the chosen provider (`Volo.Abp.EntityFrameworkCore.PostgreSql`, `.MySQL`, `.Oracle`, `.Sqlite`).
2. In `MyProjectNameEntityFrameworkCoreModule` swap `options.UseSqlServer()` for `options.UseNpgsql()` etc.
3. In `MyProjectNameDbContextFactory` swap `.UseSqlServer(...)` for the matching call.
4. Delete the existing `Migrations/` folder and run `dotnet ef migrations add Initial`.

The template ships `//<TEMPLATE-REMOVE IF-NOT='dbms:PostgreSQL'>` blocks that toggle `AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true)` for PostgreSQL — these markers are processed by `abp new`; in already-generated solutions they appear as comments and can be safely removed.

## Customization points

| Need                                  | File / API                                                       |
| ------------------------------------- | ---------------------------------------------------------------- |
| Map a new aggregate                   | `OnModelCreating` block in `MyProjectNameDbContext`              |
| Generate a migration                  | `dotnet ef migrations add <Name>` from this project              |
| Add an EF-mapped extension property   | `MyProjectNameEfCoreEntityExtensionMappings`                     |
| Replace a module's repository         | `context.Services.AddTransient<IMyEntityRepository, ...>()` in the module |
| Disable transactional UoW             | `Configure<AbpUnitOfWorkDefaultOptions>(...)`                    |

## Gotchas

- **`ReplaceDbContext` is permanent.** Once you replace `IIdentityDbContext` you cannot have a separate Identity database — all Identity tables go into the application's database. Multi-database scenarios require multiple `DbContext` classes; the [Volo docs on Multiple DbContext](https://docs.abp.io/en/abp/latest/Entity-Framework-Core-Multiple-DbContext) explain the trade-offs.
- **The design-time factory points at `DbMigrator/appsettings.json`.** If you change the migrator's connection string but not the API host's, `dotnet ef database update` and the runtime will diverge. Keep both files in sync or move the connection string into User Secrets.
- **`includeAllEntities: true` exposes module-internal entities** as `IRepository<T>`. Convenient, but discourages the DDD habit of accessing aggregates only through their root. Switch it off for new greenfield projects.
- **Migrations live in this project.** Running `Add-Migration` from another folder generates the files at the wrong path. Either `cd` into this directory or pass `--project src/MyCompanyName.MyProjectName.EntityFrameworkCore` to the ABP CLI's `update-database` command.
- **OpenIddict tables are managed here.** Deleting OpenIddict-related migrations breaks the `OpenIddictDataSeedContributor` in `Domain` — the seed call assumes the tables exist.
- **PostgreSQL requires `Npgsql.EnableLegacyTimestampBehavior`** for ABP audit fields. The template sets it both in the module's `PreConfigureServices` and in the design-time factory; removing one breaks runtime, removing the other breaks tooling.
