`Volo.Abp.Identity.HttpApi` ships four MVC controllers — three under
`api/identity` and one under `integration-api/identity`. They all carry
`[Area(IdentityRemoteServiceConsts.ModuleName)]` (`"identity"`) and the
matching `[RemoteService]`. The `[Authorize]` attributes live on the
application-service implementation (`IdentityUserAppService`,
`IdentityRoleAppService`), so the table below lists the policy that the
service requires at runtime.

```text Volo.Abp.Identity.HttpApi
Volo/Abp/Identity/
├── IdentityUserController.cs        → /api/identity/users
├── IdentityRoleController.cs        → /api/identity/roles
├── IdentityUserLookupController.cs  → /api/identity/users/lookup
└── Integration/IdentityUserIntegrationController.cs
                                       → /integration-api/identity/users
```

### Integration (machine-to-machine)

| Verb | Path | Body | Returns | Policy |
| ---- | ---- | ---- | ------- | ------ |
| GET  | `/integration-api/identity/users/{id}/role-names` | — | `string[]` | none (intended for trusted callers) |

The `integration-api` prefix is wired by
`IntegrationServiceAttribute` so integration controllers can be called by
microservices without forwarding the user identity.

## IdentityUserController

```csharp modules/identity/src/Volo.Abp.Identity.HttpApi/Volo/Abp/Identity/IdentityUserController.cs
[RemoteService(Name = IdentityRemoteServiceConsts.RemoteServiceName)]
[Area(IdentityRemoteServiceConsts.ModuleName)]
[ControllerName("User")]
[Route("api/identity/users")]
public class IdentityUserController : AbpControllerBase, IIdentityUserAppService
{
    [HttpGet]
    public virtual Task<PagedResultDto<IdentityUserDto>> GetListAsync(GetIdentityUsersInput input)
        => UserAppService.GetListAsync(input);

    [HttpGet]
    [Route("{id}")]
    public virtual Task<IdentityUserDto> GetAsync(Guid id) => UserAppService.GetAsync(id);

    [HttpPost]
    public virtual Task<IdentityUserDto> CreateAsync(IdentityUserCreateDto input)
        => UserAppService.CreateAsync(input);

    [HttpPut]
    [Route("{id}")]
    public virtual Task<IdentityUserDto> UpdateAsync(Guid id, IdentityUserUpdateDto input)
        => UserAppService.UpdateAsync(id, input);

    [HttpDelete]
    [Route("{id}")]
    public virtual Task DeleteAsync(Guid id) => UserAppService.DeleteAsync(id);

    [HttpGet]
    [Route("{id}/roles")]
    public virtual Task<ListResultDto<IdentityRoleDto>> GetRolesAsync(Guid id)
        => UserAppService.GetRolesAsync(id);

    [HttpGet]
    [Route("assignable-roles")]
    public Task<ListResultDto<IdentityRoleDto>> GetAssignableRolesAsync()
        => UserAppService.GetAssignableRolesAsync();

    [HttpPut]
    [Route("{id}/roles")]
    public virtual Task UpdateRolesAsync(Guid id, IdentityUserUpdateRolesDto input)
        => UserAppService.UpdateRolesAsync(id, input);

    [HttpGet]
    [Route("by-username/{userName}")]
    public virtual Task<IdentityUserDto> FindByUsernameAsync(string userName)
        => UserAppService.FindByUsernameAsync(userName);

    [HttpGet]
    [Route("by-email/{email}")]
    public virtual Task<IdentityUserDto> FindByEmailAsync(string email)
        => UserAppService.FindByEmailAsync(email);
}
```

### `GET /api/identity/users/assignable-roles`

Returns the roles where `IsPublic = true` — used by the user-edit screen to
populate the role picker without leaking internal roles.

## Permission definitions

```csharp modules/identity/src/Volo.Abp.Identity.Application.Contracts/Volo/Abp/Identity/IdentityPermissions.cs
public static class IdentityPermissions
{
    public const string GroupName = "AbpIdentity";

    public static class Roles
    {
        public const string Default = GroupName + ".Roles";
        public const string Create = Default + ".Create";
        public const string Update = Default + ".Update";
        public const string Delete = Default + ".Delete";
        public const string ManagePermissions = Default + ".ManagePermissions";
    }

    public static class Users
    {
        public const string Default = GroupName + ".Users";
        public const string Create = Default + ".Create";
        public const string Update = Default + ".Update";
        public const string Delete = Default + ".Delete";
        public const string ManagePermissions = Default + ".ManagePermissions";
    }

    public static class UserLookup
    {
        public const string Default = GroupName + ".UserLookup";
    }
}
```

`IdentityUserAppService` carries `[Authorize(IdentityPermissions.Users.Default)]`
at class level plus the create/update/delete overrides shown in the table.
`IdentityRoleAppService` follows the same pattern with `AbpIdentity.Roles`.

## Multi-tenancy

Every endpoint above honours the `__tenant` resolver. A host-side admin can
manage a tenant's users by sending `__tenant: <name|guid>`:

```http
GET /api/identity/users HTTP/1.1
__tenant: contoso
Authorization: Bearer ...
```

When the calling token already carries a `tenantid` claim, that claim wins
and `__tenant` is ignored — clients in a tenant context can never escalate
into the host or another tenant.

Role names are unique **per tenant**; static roles (`IsStatic = true`) are
seeded by `IdentityDataSeeder` for every tenant on creation.
