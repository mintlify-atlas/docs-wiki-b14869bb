`Volo.Abp.IdentityServer.Domain.Shared` is the deepest layer of the IdentityServer4 module family. It carries nothing that depends on EF Core, MongoDB, ASP.NET Core, or even the IdentityServer4 library itself — it is a contract package safe to reference from any other layer (including HTTP clients that only need to deserialize an ETO). The Domain layer (`Volo.Abp.IdentityServer.Domain`) takes a hard dependency on it; so do the Pro Application.Contracts and Application packages and any consumer of distributed entity events.

This page maps the directory, walks the constants, ETOs and extension registry, and lists the localization keys you'd commonly need.

## The module class

`AbpIdentityServerDomainSharedModule` is a marker that depends on the standard ABP infrastructure modules (validation, virtual file system, localization) and registers the embedded localization JSON files plus the `AbpIdentityServerResource` token. Other modules `[DependsOn(typeof(AbpIdentityServerDomainSharedModule))]` so they automatically get the strings and the extension-property registry.

## Column-length constants

Every aggregate has a sidecar `XxxConsts` class so that **both** the EF Core fluent configuration and any UI form can read the same max lengths. The values are mutable `static int` properties so a host can crank them up at startup before model creation.

```csharp
// Volo/Abp/IdentityServer/Clients/ClientConsts.cs
public class ClientConsts
{
    public static int ClientIdMaxLength { get; set; } = 200;
    public static int ProtocolTypeMaxLength { get; set; } = 200;
    public static int ClientNameMaxLength { get; set; } = 200;
    public static int ClientUriMaxLength { get; set; } = 2000;
    public static int LogoUriMaxLength { get; set; } = 2000;
    public static int DescriptionMaxLength { get; set; } = 1000;
    public static int FrontChannelLogoutUriMaxLength { get; set; } = 2000;
    public static int BackChannelLogoutUriMaxLength { get; set; } = 2000;
    public static int ClientClaimsPrefixMaxLength { get; set; } = 200;
    public static int PairWiseSubjectSaltMaxLength { get; set; } = 200;
    public static int UserCodeTypeMaxLength { get; set; } = 100;
    public static int AllowedIdentityTokenSigningAlgorithms { get; set; } = 100;
}
```

### Why mutable static?

EF Core reads them at `OnModelCreating` time (see [`IdentityServer EF Core`](/modules/authservers/identityserver-efcore)). MongoDB ignores them. **Mutating them after the DbContext model is built has no effect** — bump them in your `[DependsOn]` module's `PreConfigureServices` before any `DbContext` is materialised.

## Distributed Entity Events (ETOs)

The Domain.Shared package contains three event-transfer-object (ETO) types that the Domain module wires into `AbpDistributedEntityEventOptions.EtoMappings`:

| ETO | Source entity | Use case |
| --- | --- | --- |
| `ClientEto` | `Client` | Cache invalidation on Client updates across nodes; downstream services that mirror client list |
| `ApiResourceEto` | `ApiResource` | Same — ApiResource discovery cache |
| `IdentityResourceEto` | `IdentityResource` | Identity resource list refresh |
| `DeviceFlowCodesEto` | `DeviceFlowCodes` | Device flow polling/log emission |
| `PersistedGrantEto` | `PersistedGrant` | Optional — token cleanup or downstream auditing |

`ClientEto` is a flat mirror of every scalar property on `Client`:

```csharp
// Volo/Abp/IdentityServer/Clients/ClientEto.cs (excerpt)
[Serializable]
public class ClientEto
{
    public Guid Id { get; set; }
    public string ClientId { get; set; }
    public string ClientName { get; set; }
    public string Description { get; set; }
    public string ClientUri { get; set; }
    public string LogoUri { get; set; }
    public bool Enabled { get; set; } = true;
    public string ProtocolType { get; set; }
    public bool RequireClientSecret { get; set; }
    public bool RequireConsent { get; set; }
    public bool AllowRememberConsent { get; set; }
    public bool AlwaysIncludeUserClaimsInIdToken { get; set; }
    public bool RequirePkce { get; set; }
    public bool AllowPlainTextPkce { get; set; }
    public bool AllowAccessTokensViaBrowser { get; set; }
    public string FrontChannelLogoutUri { get; set; }
    public bool FrontChannelLogoutSessionRequired { get; set; }
    public string BackChannelLogoutUri { get; set; }
    public bool BackChannelLogoutSessionRequired { get; set; }
    public bool AllowOfflineAccess { get; set; }
    public int IdentityTokenLifetime { get; set; }
    public int AccessTokenLifetime { get; set; }
    public int AuthorizationCodeLifetime { get; set; }
    public int? ConsentLifetime { get; set; }
    public int AbsoluteRefreshTokenLifetime { get; set; }
    public int SlidingRefreshTokenLifetime { get; set; }
    public int RefreshTokenUsage { get; set; }
    public bool UpdateAccessTokenClaimsOnRefresh { get; set; }
    public int RefreshTokenExpiration { get; set; }
    public int AccessTokenType { get; set; }
    // … (full list — child collections are NOT projected on the ETO)
}
```

> **Gotcha — collections are not on the ETO.** `AllowedScopes`, `ClientSecrets`, `RedirectUris`, etc. are intentionally absent. The ETO only carries the aggregate's scalar surface; subscribers who need the full graph must reload from the repository.

Subscribers wire up like any other ABP distributed event handler:

```csharp
public class ClientCacheInvalidator
    : IDistributedEventHandler<EntityUpdatedEto<ClientEto>>,
      IDistributedEventHandler<EntityDeletedEto<ClientEto>>,
      ITransientDependency
{
    private readonly IDistributedCache<ClientDescriptor> _cache;

    public async Task HandleEventAsync(EntityUpdatedEto<ClientEto> evt)
        => await _cache.RemoveAsync(evt.Entity.ClientId);

    public async Task HandleEventAsync(EntityDeletedEto<ClientEto> evt)
        => await _cache.RemoveAsync(evt.Entity.ClientId);
}
```

## Security log action constants

`IdentityServerSecurityLogActionConsts` is the canonical list of action names that get written to the **security log** when a user signs in through the IdentityServer4 flow. These line up with the result branches inside `AbpResourceOwnerPasswordValidator` (Domain layer).

```csharp
public class IdentityServerSecurityLogActionConsts
{
    public static string LoginSucceeded { get; set; } = "LoginSucceeded";
    public static string LoginLockedout { get; set; } = "LoginLockedout";
    public static string LoginNotAllowed { get; set; } = "LoginNotAllowed";
    public static string LoginRequiresTwoFactor { get; set; } = "LoginRequiresTwoFactor";
    public static string LoginFailed { get; set; } = "LoginFailed";
    public static string LoginInvalidUserName { get; set; } = "LoginInvalidUserName";
    public static string LoginInvalidUserNameOrPassword { get; set; } = "LoginInvalidUserNameOrPassword";
}
```

`IdentityServerSecurityLogIdentityConsts.IdentityServer = "IdentityServer"` is the `Identity` discriminator that gets written into `AbpSecurityLogs.Identity` so you can filter login attempts coming through the auth-server from those coming through the regular MVC login.

## The extension-property registry

```csharp
public static class IdentityServerModuleExtensionConsts
{
    public const string ModuleName = "IdentityServer";

    public static class EntityNames
    {
        public const string Client = "Client";
        public const string IdentityResource = "IdentityResource";
        public const string ApiResource = "ApiResource";
        public const string ApiScope = "ApiScope";
    }
}
```

These string keys identify the entity slots inside the global `ObjectExtensionManager`. They feed into `IdentityServerModuleExtensionConfiguration` / `…ConfigurationDictionaryExtensions`, which are the same shape ABP uses for the Identity, Account, and CMS-Kit modules. A typical host extension looks like:

```csharp
ObjectExtensionManager.Instance.Modules()
    .ConfigureIdentityServer(identityServer =>
    {
        identityServer.ConfigureClient(client =>
        {
            client.AddOrUpdateProperty<string>("InternalNotes",
                property => { property.Attributes.Add(new MaxLengthAttribute(2048)); });
        });
    });
```

> **Note.** `DeviceFlowCodes` and `PersistedGrant` are **not** in the registry — they're internal protocol state, not user-facing aggregates. If you genuinely need to attach extension properties there, you'd have to extend the EF mapping yourself.

## Localization resources

`AbpIdentityServerResource` is the typed handle. The JSON files under `Localization/Resources/` are wired through the module class. The English file (`en.json`) is the source of truth; every other culture is a sibling. Keys are grouped by feature (login validation, consent prompt, error messages) and translated into 30+ languages including ar, cs, de, el, en-GB, es, fa, fi, FR, hi, hu, is, it, nl, pl-PL, pt-BR, ro-RO, ru, sk, sl, tr, vi, zh-Hans, zh-Hant.

Resolve a string from anywhere:

```csharp
public class MyService : ITransientDependency
{
    private readonly IStringLocalizer<AbpIdentityServerResource> _l;
    public MyService(IStringLocalizer<AbpIdentityServerResource> l) => _l = l;

    public string LoginFailureMessage() => _l["LoginFailed"];
}
```

## Gotchas

- **Don't reference IdentityServer4 here.** This package must remain free of IdentityServer4 types so it can be referenced from front-end / contracts / messaging projects. The actual IS4 types only appear in the Domain layer.
- **Tweak consts in `PreConfigureServices`.** Static-property mutation after the EF model is built is silently ignored.
- **ETOs are flat.** Don't expect to navigate child collections off `ClientEto`; reload from repository if you need them.
- **Security log strings are mutable statics.** If you reassign `IdentityServerSecurityLogActionConsts.LoginFailed = "AuthLogin.Failed"`, all writes after that point will use the new string. Don't do this after the application has been running — the historical log will be unsearchable.
