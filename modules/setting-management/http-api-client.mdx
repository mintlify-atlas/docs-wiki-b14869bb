The HTTP API client package generates strongly-typed C# proxies for `IEmailSettingsAppService` and `ITimeZoneSettingsAppService`. Server-side hosts can use these for service-to-service calls. Blazor WebAssembly, MAUI, and console apps reference this package to consume the module through HTTPS.

```csharp
[DependsOn(
    typeof(AbpSettingManagementApplicationContractsModule),
    typeof(AbpHttpClientModule))]
public class AbpSettingManagementHttpApiClientModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        context.Services.AddStaticHttpClientProxies(
            typeof(AbpSettingManagementApplicationContractsModule).Assembly,
            SettingManagementRemoteServiceConsts.RemoteServiceName
        );

        Configure<AbpVirtualFileSystemOptions>(options =>
        {
            options.FileSets.AddEmbedded<AbpSettingManagementHttpApiClientModule>();
        });
    }
}
```

The first call is what triggers registration of every type that implements `IApplicationService` in `AbpSettingManagementApplicationContractsModule`'s assembly — it scans the assembly for service interfaces and binds them to generated `ClientProxyBase<T>` implementations. The second call is for the embedded `application-configuration.json` localization fragments shipped with this assembly.

The four `ClientProxies/...` files are a *partial class pair* per service. `.Generated.cs` is regenerated by the ABP CLI from the live OpenAPI spec; the non-generated half is the customization seam.

## `EmailSettingsClientProxy.Generated.cs`

```csharp
[Dependency(ReplaceServices = true)]
[ExposeServices(typeof(IEmailSettingsAppService), typeof(EmailSettingsClientProxy))]
public partial class EmailSettingsClientProxy : ClientProxyBase<IEmailSettingsAppService>, IEmailSettingsAppService
{
    public virtual async Task<EmailSettingsDto> GetAsync()
    {
        return await RequestAsync<EmailSettingsDto>(nameof(GetAsync));
    }

    public virtual async Task UpdateAsync(UpdateEmailSettingsDto input)
    {
        await RequestAsync(nameof(UpdateAsync), new ClientProxyRequestTypeValue
        {
            { typeof(UpdateEmailSettingsDto), input }
        });
    }

    public virtual async Task SendTestEmailAsync(SendTestEmailInput input)
    {
        await RequestAsync(nameof(SendTestEmailAsync), new ClientProxyRequestTypeValue
        {
            { typeof(SendTestEmailInput), input }
        });
    }
}
```

Three pieces of magic:

* **`[Dependency(ReplaceServices = true)]`** ensures the proxy *replaces* any local registration of `IEmailSettingsAppService`. In a hybrid host that hosts the API itself, this attribute would cause infinite recursion; that's why server-side hosts do not reference `HttpApi.Client`.
* **`[ExposeServices(IEmailSettingsAppService, EmailSettingsClientProxy)]`** registers the proxy under both interfaces. Consumers can inject either the contract (`IEmailSettingsAppService`) or the concrete proxy (`EmailSettingsClientProxy`) for advanced scenarios.
* **`RequestAsync(nameof(GetAsync))`** uses the method name as the routing key. The framework's `ClientProxyApiDescriptionFinder` resolves the name against the API description (delivered through `IApiDescriptionFinder` — either the static `/api/abp/api-definition` cache or a build-time generated description file).

The route, HTTP verb, and request shape are *not* in the proxy. They are looked up from the API description at runtime. So if `AbpSettingManagementHttpApiModule` changes a route attribute, the client doesn't need recompilation — it'll pick up the change the next time its API-definition cache refreshes.

### `ClientProxyRequestTypeValue`

This shape is how the proxy passes complex inputs. For methods with a single DTO parameter it's a one-element dictionary keyed by the DTO type. For methods with multiple parameters it's keyed by each parameter type. The proxy maps each entry to the correct HTTP location (body, query, route) based on the API description.

## `EmailSettingsClientProxy.cs` — customization seam

```csharp
// This file is part of EmailSettingsClientProxy, you can customize it here
namespace Volo.Abp.SettingManagement;

public partial class EmailSettingsClientProxy
{
}
```

The empty file is where you add overrides:

```csharp
public partial class EmailSettingsClientProxy
{
    public override async Task<EmailSettingsDto> GetAsync()
    {
        var dto = await base.GetAsync();
        // strip the password for client-side display
        dto.SmtpPassword = null;
        return dto;
    }
}
```

Customizations survive proxy regeneration because the ABP CLI only rewrites `.Generated.cs`.

## `TimeZoneSettingsClientProxy.Generated.cs`

Same shape, three methods:

```csharp
public virtual async Task<string> GetAsync() => await RequestAsync<string>(nameof(GetAsync));

public virtual async Task<List<NameValue>> GetTimezonesAsync()
    => await RequestAsync<List<NameValue>>(nameof(GetTimezonesAsync));

public virtual async Task UpdateAsync(string timezone)
    => await RequestAsync(nameof(UpdateAsync), new ClientProxyRequestTypeValue
    {
        { typeof(string), timezone }
    });
```

The `string` parameter for `UpdateAsync` makes `ClientProxyRequestTypeValue` ambiguous in any future method that takes two `string`s — but for now it's unambiguous because there's only the one parameter.

## Configuration

The proxies need a `RemoteServices` block in `appsettings.json`:

```json
{
  "RemoteServices": {
    "SettingManagement": {
      "BaseUrl": "https://api.contoso.com/"
    },
    "Default": {
      "BaseUrl": "https://api.contoso.com/"
    }
  }
}
```

The lookup order is the remote-service name (`SettingManagement`) first, then `Default` if absent. Mismatches between the `BaseUrl` and the controller route mean `https://api.contoso.com/api/setting-management/emailing` is the final URL — the proxy does not include `/api/...` itself, the API description does.

If your hosting model serves the API under a sub-path (e.g. `https://contoso.com/admin-api/...`), set `BaseUrl` accordingly. The proxies will compose `https://contoso.com/admin-api/api/setting-management/emailing`.

### Authentication

The proxies send the `Authorization` header through the `IHttpClientFactory`-managed `HttpClient`. ABP's `IdentityModel` integration provides a `IdentityModelHttpClientHandler` that fetches OAuth2 tokens. Wire it up via:

```csharp
context.Services.AddTransient<IdentityModelHttpClientHandler>();
Configure<AbpHttpClientBuilderOptions>(options =>
{
    options.ProxyClientBuildActions.Add((name, client) =>
    {
        client.AddHttpMessageHandler<IdentityModelHttpClientHandler>();
    });
});
```

For Blazor WebAssembly, the standard pattern is `AddOidcAuthentication` plus `AddAccessTokenManagement`, which injects bearer tokens into `HttpClient`s named after the remote service.

## Embedded files

`AddEmbedded<AbpSettingManagementHttpApiClientModule>()` ships embedded localization fragments inside the assembly. The package includes a `client-proxies` virtual file for some surfaces, but for setting-management specifically the embedded assets are minimal — mostly a placeholder to keep the assembly virtual-file-system-aware.

## Custom HTTP client behavior

You can apply a per-remote-service named `HttpClient` build action:

```csharp
Configure<AbpHttpClientBuilderOptions>(options =>
{
    options.ProxyClientBuildActions.Add((remoteServiceName, builder) =>
    {
        if (remoteServiceName == SettingManagementRemoteServiceConsts.RemoteServiceName)
        {
            builder.ConfigureHttpClient(c =>
            {
                c.Timeout = TimeSpan.FromSeconds(30);
            });
        }
    });
});
```

The build action runs once per named `HttpClient` (one per remote service), so it's a sensible place to add `Polly` retry policies or to redirect SMTP-heavy setting reads to a longer timeout.

## Gotchas

* **Never reference `HttpApi.Client` *and* `HttpApi` from the same host.** The proxy's `[Dependency(ReplaceServices = true)]` registers a `ClientProxyBase` against `IEmailSettingsAppService`, which would replace the *real* server-side service. Hosts that expose the API directly should not pull in the client.
* **Static proxies require API descriptions.** The framework discovers them either via `/api/abp/api-definition` (live) or via the `Volo.Abp.Http.Client.ClientProxying` source generator at build time. Air-gapped clients without network access at startup need the build-time path.
* **`ClientProxyRequestTypeValue` is order-sensitive for methods with multiple same-typed parameters.** If a future overload of `UpdateAsync` takes `(string timezone, string note)`, the dictionary keyed by `typeof(string)` collapses. Use distinct DTO types.
* **`virtual` on every method matters.** The methods are `virtual` precisely so you can override them in `.cs` (not `.Generated.cs`) without regen breakage. Don't seal them in your overrides if you need further extension.
* **Localization JSON files travel inside the assembly.** If you fork the client module, keep the `<EmbeddedResource>` directive in the `.csproj` or the resource files vanish at runtime.

## Static vs. dynamic proxies

ABP supports two proxy generation strategies:

| Strategy | Mechanism | Trade-offs |
| --- | --- | --- |
| **Static** (this package) | Code-generated at build time via `AddStaticHttpClientProxies`, with `.Generated.cs` files committed to the repo. | Zero runtime overhead, AOT-friendly, traceable in source control. Requires regeneration when the API surface changes. |
| **Dynamic** | Runtime DispatchProxy created from `IApiDescriptionFinder`, requested via `AddHttpClientProxies`. | Always in sync with the API. Slower (reflection on every call), unfriendly to WebAssembly AOT. |

The setting management module ships with static proxies because:

1. The API surface is *stable* — six methods across two services that rarely change.
2. WebAssembly AOT compilation rejects the dynamic proxy's runtime `Emit` calls.
3. The static files double as documentation — readers can see the exact method signature without reverse-engineering an interceptor.

If you wanted dynamic instead, you'd skip this module and call `context.Services.AddHttpClientProxies(typeof(AbpSettingManagementApplicationContractsModule).Assembly, RemoteServiceName)` in your own module. There is no advantage in mixing the two.

## Inspecting proxy resolution at runtime

When debugging a proxy mismatch, the relevant DI registrations are:

```text
IEmailSettingsAppService -> EmailSettingsClientProxy   (transient, replaceServices=true)
EmailSettingsClientProxy -> EmailSettingsClientProxy   (transient, exposed alias)
```

Both come from the `[ExposeServices]` attribute on `.Generated.cs`. You can validate by injecting `IServiceProvider`:

```csharp
var proxy = sp.GetRequiredService<IEmailSettingsAppService>();
Console.WriteLine(proxy.GetType().FullName);
// Volo.Abp.SettingManagement.EmailSettingsClientProxy
```

If the printed type is `Castle.Proxies.IEmailSettingsAppServiceProxy` instead, your host has accidentally pulled in both the server and client implementations and Castle's dynamic proxy wrapped the dynamic-API-finder version.
