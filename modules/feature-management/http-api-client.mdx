`Volo.Abp.FeatureManagement.HttpApi.Client` is the static-typed HTTP client proxy for `IFeatureAppService`. A consumer (Blazor WASM, MAUI, console worker, microservice gateway acting as a client) references this assembly and gets a working `IFeatureAppService` injected — every call serializes to the REST endpoints documented in [http-api](/modules/feature-management/http-api).

Module class:

```csharp
[DependsOn(
    typeof(AbpFeatureManagementApplicationContractsModule),
    typeof(AbpHttpClientModule))]
public class AbpFeatureManagementHttpApiClientModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        context.Services.AddStaticHttpClientProxies(
            typeof(AbpFeatureManagementApplicationContractsModule).Assembly,
            FeatureManagementRemoteServiceConsts.RemoteServiceName
        );

        Configure<AbpVirtualFileSystemOptions>(options =>
        {
            options.FileSets.AddEmbedded<AbpFeatureManagementHttpApiClientModule>();
        });
    }
}
```

Two relevant pieces:

- **`AddStaticHttpClientProxies(Assembly, remoteServiceName)`** — scans the application-contracts assembly for `[ExposeServices(typeof(...))]` partial classes deriving from `ClientProxyBase<T>` and wires each as the registered implementation of the corresponding interface. The `remoteServiceName = "AbpFeatureManagement"` is the key into `AbpRemoteServiceOptions.RemoteServices` for base-URL lookup.
- **Embedded file set** — the client proxy assembly carries embedded localization JSON for offline scenarios. Mostly relevant in Blazor WASM bundles.

## File inventory

| Path | Role |
| --- | --- |
| `AbpFeatureManagementHttpApiClientModule.cs` | Module class. |
| `ClientProxies/Volo/Abp/FeatureManagement/FeaturesClientProxy.Generated.cs` | Auto-generated `partial class` — implements `IFeatureAppService`. |
| `ClientProxies/Volo/Abp/FeatureManagement/FeaturesClientProxy.cs` | The user-extension `partial class` — empty stub for custom code. |

The `Generated.cs` file carries this header:

> `// This file is automatically generated by ABP framework to use MVC Controllers from CSharp`

Generation is via the ABP CLI's `abp generate-proxy -t csharp -m featureManagement` against a running API host. The generated content mirrors `IFeatureAppService` exactly — same parameter names, same DTOs, same `[Dependency]` registration.

## `FeaturesClientProxy.Generated`

```csharp
[Dependency(ReplaceServices = true)]
[ExposeServices(typeof(IFeatureAppService), typeof(FeaturesClientProxy))]
public partial class FeaturesClientProxy : ClientProxyBase<IFeatureAppService>, IFeatureAppService
{
    public virtual async Task<GetFeatureListResultDto> GetAsync(string providerName, string providerKey)
    {
        return await RequestAsync<GetFeatureListResultDto>(nameof(GetAsync), new ClientProxyRequestTypeValue
        {
            { typeof(string), providerName },
            { typeof(string), providerKey }
        });
    }

    public virtual async Task UpdateAsync(string providerName, string providerKey, UpdateFeaturesDto input)
    {
        await RequestAsync(nameof(UpdateAsync), new ClientProxyRequestTypeValue
        {
            { typeof(string), providerName },
            { typeof(string), providerKey },
            { typeof(UpdateFeaturesDto), input }
        });
    }

    public virtual async Task DeleteAsync(string providerName, string providerKey)
    {
        await RequestAsync(nameof(DeleteAsync), new ClientProxyRequestTypeValue
        {
            { typeof(string), providerName },
            { typeof(string), providerKey }
        });
    }
}
```

### `[Dependency(ReplaceServices = true)]` + `[ExposeServices(...)]`

Together these make `FeaturesClientProxy` the *replacement* registration for `IFeatureAppService`. In a host that depends on `AbpFeatureManagementApplicationModule` and `AbpFeatureManagementHttpApiClientModule` in the same DI container, the client proxy wins — the in-proc `FeatureAppService` is silently shadowed. **In practice these two modules should never coexist** in the same process; it's why microservice templates put the application module in the API host and the client module in the gateway/UI host.

`typeof(FeaturesClientProxy)` is also exposed so consumers can inject the concrete type if they want to override behaviour without re-implementing the interface.

### `ClientProxyBase<T>.RequestAsync`

The `RequestAsync` helper, in `Volo.Abp.Http.Client.ClientProxying`, does the heavy lifting:

1. Looks up the action description for `IFeatureAppService.{methodName}` in `IApiDescriptionFinder`. That description was discovered server-side from the controller's metadata and is cached in-process; if you regenerated the static proxy without the server's `/abp/api-definition` being current, parameter binding could go wrong (rare in practice — the generator and server agree because they share `AbpFeatureManagementApplicationContractsModule`).
2. Builds the HTTP request — `GET` with query-string for `GetAsync/DeleteAsync`, `PUT` with JSON body for `UpdateAsync`.
3. Resolves the base URL via `AbpRemoteServiceOptions.RemoteServices[RemoteServiceName]`, falling back to `"Default"`.
4. Acquires auth via `IHttpClientAuthenticator` (typically the OpenID Connect token cache).
5. Serializes the body with the framework's `IJsonSerializer`, which in turn uses `AbpSystemTextJsonSerializerOptions` — *including* the polymorphic `IStringValueType` converter registered in Domain.Shared. So `UpdateFeaturesDto` round-trips correctly even though `UpdateFeatureDto.Value` is a plain string (no polymorphism on the request side).
6. Deserializes the response into `GetFeatureListResultDto` — *here* the polymorphic converter matters, because `FeatureDto.ValueType` is `IStringValueType`.

### `ClientProxyRequestTypeValue`

This is a list of `(type, value)` tuples preserving parameter order — the framework uses the API description to map each tuple to the corresponding parameter name. Because the proxy uses the *parameter type* rather than the parameter name as the key, two `string` parameters in a row (`providerName` and `providerKey`) need to be added in declaration order. If you ever rearrange the parameter order of `IFeatureAppService.GetAsync` and regenerate the proxy, the dictionary additions follow — but if you edit the interface and forget to regenerate, the proxy compiles but mis-binds the arguments.

## `FeaturesClientProxy` (extension stub)

```csharp
public partial class FeaturesClientProxy
{
}
```

The empty partial class lets consumers add custom methods or override the generated `virtual` ones without editing the generated file. Common reasons to extend:

- Custom retry policies (Polly wrapper around `RequestAsync`).
- Adding analytics — log every `UpdateAsync` call to a feature-flag audit trail.
- Layering a local cache on top of `GetAsync` when the WASM client wants to avoid re-fetching every navigation.

Example extension:

```csharp
public partial class FeaturesClientProxy
{
    public override async Task<GetFeatureListResultDto> GetAsync(string providerName, string providerKey)
    {
        var cacheKey = $"{providerName}:{providerKey}";
        if (_localCache.TryGetValue(cacheKey, out var cached) &&
            DateTimeOffset.UtcNow - cached.AsOf < TimeSpan.FromSeconds(30))
        {
            return cached.Value;
        }

        var fresh = await base.GetAsync(providerName, providerKey);
        _localCache[cacheKey] = (fresh, DateTimeOffset.UtcNow);
        return fresh;
    }
}
```

## Configuration

The host's `appsettings.json` needs the remote service endpoint:

```json
{
  "RemoteServices": {
    "Default": {
      "BaseUrl": "https://my-api.example.com/"
    },
    "AbpFeatureManagement": {
      "BaseUrl": "https://my-admin-api.example.com/"
    }
  }
}
```

If `AbpFeatureManagement` is absent, the proxy falls back to `Default`. In a single-host setup (one API serving everything) only `Default` is necessary. In microservices, point `AbpFeatureManagement` at the Administration service.

`AbpHttpClientModule` reads `AbpRemoteServiceOptions` from configuration via the `IConfiguration` binding pattern, so no code is required beyond depending on the module.

## Auth header propagation

The framework's `IHttpClientAuthenticator` populates the `Authorization` header with the *current* user's bearer token. In a Blazor WASM hosted under OpenIddict, that means the token attached when an admin clicks "Manage features" on the tenant page. The receiving API uses the same token for authentication and runs `FeatureAppService.CheckProviderPolicy` against the user's claims.

If you call `FeaturesClientProxy` from a background worker without a current user, you'll need to register a custom `IHttpClientAuthenticator` to attach a client-credentials token. The framework ships `IdentityModel.AspNetCore.ClientCredentialsTokenManagementBuilderExtensions` patterns for this; you wire it in your worker's module class.

## Static vs. dynamic proxies

ABP supports two proxy generation modes:

| Style | Where | Generation |
| --- | --- | --- |
| Static | `FeaturesClientProxy.Generated.cs` | Generated by `abp generate-proxy` at build time. AOT-compatible. |
| Dynamic | `Volo.Abp.Http.Client.DynamicProxying` (always available) | Generated at runtime via Castle.Core dynamic proxies. Resolves through `IApiDescriptionFinder` over the same `IApiDescriptionCache`. |

Both can coexist. If the static proxy is registered (as in this module), it wins because of `ReplaceServices = true`. If a project references only `AbpFeatureManagementApplicationContractsModule` and `AbpHttpClientModule` without the HttpApi.Client module, the dynamic proxy kicks in. Both reach the same controller, so behaviour is identical — but the static proxy is *AOT-safe*, which matters in Blazor WASM ahead-of-time scenarios.

## Composition with the HTTP API host

A single ABP solution typically lays out:

| Project | References |
| --- | --- |
| `MyApp.HttpApi.Host` | `AbpFeatureManagementApplication`, `AbpFeatureManagementHttpApi`. |
| `MyApp.Blazor.Server` | `AbpFeatureManagementApplication`, `AbpFeatureManagementBlazor`. |
| `MyApp.Blazor` (WASM) | `AbpFeatureManagementHttpApiClient`, `AbpFeatureManagementBlazor`. |
| `MyApp.MauiClient` | `AbpFeatureManagementHttpApiClient`. |

Blazor Server uses the in-proc application module (no HTTP hop). Blazor WASM uses the client module (HTTP over the wire). The Blazor UI module (`AbpFeatureManagementBlazor`) carries the UI components and is identical in both flavours — only the `IFeatureAppService` registration differs.

## Method-by-method semantics

### `GetAsync(providerName, providerKey)`

- HTTP `GET /api/feature-management/features?providerName={p}&providerKey={k}`.
- `providerKey` `null` ⇒ the query string omits the parameter entirely (System.Text.Json + the framework's query-string builder skip `null`s by default). The controller binds it back to `null`.
- Returns the full `GetFeatureListResultDto`. `IStringValueType` polymorphism is preserved via `StringValueTypeJsonConverter`.

### `UpdateAsync(providerName, providerKey, input)`

- HTTP `PUT /api/feature-management/features?providerName={p}&providerKey={k}` with `input` as JSON body.
- Returns `void` (204).
- Validation errors from `FeatureManager.SetAsync` propagate as `RemoteServiceErrorResponse` → `AbpRemoteCallException` on the client. The client `ExceptionFilter` (in Blazor) maps to user-facing notifications.

### `DeleteAsync(providerName, providerKey)`

- HTTP `DELETE /api/feature-management/features?providerName={p}&providerKey={k}`.
- Returns `void` (204).
- As noted, `FeatureAppService.DeleteAsync` skips `CheckProviderPolicy` server-side — the client proxy is only the messenger.

## Gotchas

- **Do not coexist with the application module.** `[Dependency(ReplaceServices = true)]` will shadow `FeatureAppService` and cause an infinite HTTP loop if the API host accidentally references the client module.
- **Token expiry inside long-running modals.** Blazor's `FeatureManagementModal.OpenAsync` calls `GetAsync` once at open; if the user takes 10 minutes to save and the token expires in between, `UpdateAsync` fails with 401. The framework's auth handler will trigger a silent refresh — make sure the host's authority is reachable.
- **Polymorphic deserialization requires the converter.** If you reference this module from a non-ABP consumer (e.g. a raw `HttpClient` in a console app), you have to either re-register `StringValueTypeJsonConverter` on the consumer's `JsonSerializerOptions` or accept that `FeatureDto.ValueType` deserializes as `null`.
- **Static proxy regeneration is manual.** Run `abp generate-proxy -t csharp -m featureManagement -u https://my-api.example.com` after upgrading the `Volo.Abp.FeatureManagement.Application.Contracts` package. The build does not auto-regenerate.
- **`AddStaticHttpClientProxies` rescans the contracts assembly.** If you add a custom application service interface in your own application-contracts assembly, the Feature Management client module's call does *not* see it — you must register your own `AddStaticHttpClientProxies(myAssembly, "MyRemoteService")`.
- **`AbpHttpClientModule` is required transitively** for proxy registration to find `IHttpClientFactory`. The DependsOn covers this.
- For the upstream framework abstractions (`IFeatureChecker`, `IFeatureValueProvider`) that the proxied service sits in front of, see [framework/cross/features](/framework/cross/features).

## Handling stale data after a remote save

A subtle issue: the proxy invalidates the *client-side* application-configuration cache (via the modal's `ResetAsync` call), but if the server happens to be running behind a CDN-cached `/api/abp/application-configuration` endpoint (rare but seen with aggressive edge caching), the SPA sees stale data until the edge expires. Solutions:

- Set `Cache-Control: no-cache` on the application-configuration endpoint.
- Add a per-user vary header (`Vary: Authorization`) so each user has an isolated edge cache slot.
- Bump a versioning query parameter when the modal closes, e.g. `?_v={DateTime.UtcNow.Ticks}`.

None of these are responsibilities of the Feature Management module itself — but they affect the user-perceived save delay.

## Why not use the dynamic proxy everywhere?

The dynamic proxy (Castle Core) builds an IL type at runtime that implements `IFeatureAppService`. That works for JIT scenarios but breaks under Blazor WASM AOT, which disallows runtime IL emission. The static proxy compiles to plain C#, satisfies AOT, and ships smaller in the WASM payload. The trade-off is a manual regeneration step when contracts change — typically run as part of CI when the contracts assembly version bumps.

## Inspecting the registered proxy

To verify at runtime that the static proxy was registered (and not shadowed by the dynamic one):

```csharp
var service = ServiceProvider.GetRequiredService<IFeatureAppService>();
Logger.LogInformation("IFeatureAppService → {Type}", service.GetType().FullName);
```

You should see `Volo.Abp.FeatureManagement.FeaturesClientProxy`. If you see `Castle.Proxies.IFeatureAppServiceProxy`, the dynamic proxy is active — usually because `AddStaticHttpClientProxies` was called before `AbpHttpClientModule.PreConfigureServices` ran. Reorder module dependencies if this happens.

## Regenerating the static proxy

```bash
cd MyApp.Blazor              # or MyApp.HttpApi.Client project root
abp generate-proxy \
  --type csharp \
  --module featureManagement \
  --url https://my-admin-api.example.com/
```

Behaviour:

- Fetches `/api/abp/api-definition` from the API host.
- Filters by `module=featureManagement`.
- Generates `ClientProxies/Volo/Abp/FeatureManagement/FeaturesClientProxy.Generated.cs` (overwrites).
- Does **not** touch `FeaturesClientProxy.cs` (the partial extension stub).

If the API host's contracts version differs from the client's, the regeneration may produce DTO references the client can't resolve. Always keep both projects on the same `Volo.Abp.FeatureManagement.Application.Contracts` version.

## Composing with custom interceptors

The framework's `Volo.Abp.Http.Client.DelegatingHandlers` chain runs in this order:

1. `AbpHttpClientCorrelationIdHandler` — propagates `X-Correlation-Id`.
2. `AbpHttpClientCurrentTenantHandler` — propagates `__tenant` header.
3. `AbpHttpClientCultureHandler` — propagates `Accept-Language`.
4. `AbpHttpClientAuthenticateHandler` — attaches bearer token.
5. (custom handlers if registered).

For Feature Management calls, the most consequential is `AbpHttpClientCurrentTenantHandler`. If the client is in *host* context and calls `GetAsync("T", tenantGuid.ToString())`, the `__tenant` header is *not* set (host context). The API host then sees the call in host context, `CheckProviderPolicy` picks the tenant-management policy, and authorization succeeds because the calling user has `AbpTenantManagement.Tenants.ManageFeatures`.

## Static proxy and AOT trimming

The static proxy is `[Dependency(ReplaceServices = true)]`. Trimming tools may strip it if the DI container's static analysis doesn't see a direct construction. The framework's `AbpRootDescriptor` keeps it alive via explicit type list registration, but if you customise trimming aggressively, add a `DynamicDependency` attribute:

```csharp
[DynamicDependency(DynamicallyAccessedMemberTypes.All, typeof(FeaturesClientProxy))]
public class Program { /* ... */ }
```

WASM AOT scenarios benefit from this guard especially when the trimmer is set to "aggressive".

## Wire-level comparison with EF Core direct

| Aspect | EF Core direct | HTTP API client |
| --- | --- | --- |
| Latency | < 1 ms | 10–100 ms |
| Auth | Local principal | Bearer token over HTTPS |
| Cache reset propagation | `EntityChangedEventData<FeatureValue>` local event | After save, the client must call `ICurrentApplicationConfigurationCacheResetService.ResetAsync()` to clear the *client-side* cache. The API host's local invalidator handles the *server-side* cache. |
| Transactionality | Per-feature `[UnitOfWork]` | Per-HTTP-call (no transactions across the wire). |

Pick the right tier for the host. UIs in the same process as the DB use EF Core; UIs distributed across a network use the client proxy.
