`Volo.Abp.Account.Application.Contracts` is the smallest package any Account-aware host must
reference. It contains the DTOs that travel across the wire, the two application-service interfaces
(`IAccountAppService`, `IProfileAppService`), the localization resource, the
`AccountRemoteServiceConsts`, and the two account-scoped settings. Nothing in this package depends on
ASP.NET Core, EF Core, OpenIddict or any UI library — it is pure POCOs plus a module class.

This page enumerates every public type, gives the real declaration, and shows how the upstream layers
(`Application`, `HttpApi`, `HttpApi.Client`, `Blazor`) bind against these abstractions.

## Module declaration

The module depends on `AbpIdentityApplicationContractsModule` (for `IdentityUserDto`,
`IdentityUserConsts`, `IdentityModuleExtensionConsts`) and registers two cross-cutting
concerns: the `AccountResource` localization and the `Volo.Account` exception-code namespace.

```csharp
// Volo/Abp/Account/AbpAccountApplicationContractsModule.cs
[DependsOn(
    typeof(AbpIdentityApplicationContractsModule)
)]
public class AbpAccountApplicationContractsModule : AbpModule
{
    private readonly static OneTimeRunner OneTimeRunner = new OneTimeRunner();

    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        Configure<AbpVirtualFileSystemOptions>(options =>
        {
            options.FileSets.AddEmbedded<AbpAccountApplicationContractsModule>();
        });

        Configure<AbpLocalizationOptions>(options =>
        {
            options.Resources
                .Add<AccountResource>("en")
                .AddBaseTypes(typeof(AbpValidationResource))
                .AddVirtualJson("/Volo/Abp/Account/Localization/Resources");
        });

        Configure<AbpExceptionLocalizationOptions>(options =>
        {
            options.MapCodeNamespace("Volo.Account", typeof(AccountResource));
        });
    }

    public override void PostConfigureServices(ServiceConfigurationContext context)
    {
        OneTimeRunner.Run(() =>
        {
            ModuleExtensionConfigurationHelper.ApplyEntityConfigurationToApi(
                IdentityModuleExtensionConsts.ModuleName,
                IdentityModuleExtensionConsts.EntityNames.User,
                getApiTypes:    new[] { typeof(ProfileDto) },
                updateApiTypes: new[] { typeof(UpdateProfileDto) }
            );
        });
    }
}
```

The `PostConfigureServices` block wires the Identity *user* extension definitions into Account's
`ProfileDto`/`UpdateProfileDto`, so any extra property you declared on `IdentityUser` (via
`ObjectExtensionManager`) automatically appears on the profile DTO. See
[Identity application-contracts](/modules/identity/application-contracts) for the source of those
`EntityNames.User` and `ModuleName` constants.

## `AccountRemoteServiceConsts`

Two string constants used by the dynamic-proxy client, controllers, and view components:

```csharp
public static class AccountRemoteServiceConsts
{
    public const string RemoteServiceName = "AbpAccount";
    public const string ModuleName        = "account";
}
```

`RemoteServiceName` is what `AddStaticHttpClientProxies(..., AccountRemoteServiceConsts.RemoteServiceName)`
expects on the client side (see [http-api-client](/modules/account/http-api-client)). `ModuleName` is
the `[Area("account")]` on the controllers and the key
`DynamicJavaScriptProxyOptions.DisableModule("account")` uses to suppress the auto-generated jQuery
proxy in the Web project.

## `IAccountAppService`

```csharp
public interface IAccountAppService : IApplicationService
{
    Task<IdentityUserDto> RegisterAsync(RegisterDto input);

    Task SendPasswordResetCodeAsync(SendPasswordResetCodeDto input);

    Task<bool> VerifyPasswordResetTokenAsync(VerifyPasswordResetTokenInput input);

    Task ResetPasswordAsync(ResetPasswordDto input);
}
```

The interface returns Identity's own `IdentityUserDto` (from `Volo.Abp.Identity` contracts), keeping
Account a thin façade. The four members map one-to-one to the
[`AccountController`](/modules/account/http-api) routes:

| Member | HTTP verb + route |
| --- | --- |
| `RegisterAsync` | `POST /api/account/register` |
| `SendPasswordResetCodeAsync` | `POST /api/account/send-password-reset-code` |
| `VerifyPasswordResetTokenAsync` | `POST /api/account/verify-password-reset-token` |
| `ResetPasswordAsync` | `POST /api/account/reset-password` |

## `IProfileAppService`

```csharp
public interface IProfileAppService : IApplicationService
{
    Task<ProfileDto> GetAsync();

    Task<ProfileDto> UpdateAsync(UpdateProfileDto input);

    Task ChangePasswordAsync(ChangePasswordInput input);
}
```

This is the *current-user* profile, not an admin endpoint. The implementation (see
[application](/modules/account/application)) is annotated `[Authorize]` and pulls the user id from
`CurrentUser.GetId()` — there is no path parameter.

## DTOs

### `RegisterDto`

```csharp
public class RegisterDto : ExtensibleObject
{
    [Required]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxUserNameLength))]
    public string UserName { get; set; }

    [Required]
    [EmailAddress]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxEmailLength))]
    public string EmailAddress { get; set; }

    [Required]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxPasswordLength))]
    [DataType(DataType.Password)]
    [DisableAuditing]
    public string Password { get; set; }

    [Required]
    public string AppName { get; set; }
}
```

Key points:

- Inherits `ExtensibleObject`, so extra-property values defined on `IdentityUser` flow through
  `MapExtraPropertiesTo(user)` in `AccountAppService.RegisterAsync`.
- `[DynamicStringLength(typeof(IdentityUserConsts), ...)]` reads the maximum length **at validation
  time** from `IdentityUserConsts`, which itself can be overridden by setting providers — see
  [Identity domain](/modules/identity/domain).
- `[DisableAuditing]` ensures the password never lands in the audit log even if the entire DTO is
  serialized into an audit entry.
- `AppName` is mandatory and selects which app's URLs (`AppUrlOptions.Applications[appName]`) are
  used when the user is sent to the password-reset / email-confirmation flow. The Razor
  `Register.cshtml.cs` page hard-codes `AppName = "MVC"`.

### `SendPasswordResetCodeDto`

```csharp
public class SendPasswordResetCodeDto
{
    [Required]
    [EmailAddress]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxEmailLength))]
    public string Email { get; set; }

    [Required]
    public string AppName { get; set; }

    public string ReturnUrl     { get; set; }
    public string ReturnUrlHash { get; set; }
}
```

`ReturnUrl`/`ReturnUrlHash` round-trip through the reset email — when the user clicks the link they
are returned to the original destination after setting a new password. The `AccountEmailer`
URL-encodes `ReturnUrl` but treats `/connect/authorize?...` specifically to round-trip OIDC flows
correctly.

### `VerifyPasswordResetTokenInput`

```csharp
public class VerifyPasswordResetTokenInput
{
    public Guid UserId { get; set; }

    [Required]
    public string ResetToken { get; set; }
}
```

Used on the `OnGet` handler of `ResetPassword.cshtml.cs` to short-circuit the form before the user
types a new password — a common phishing/replay defense.

### `ResetPasswordDto`

```csharp
public class ResetPasswordDto
{
    public Guid UserId { get; set; }

    [Required]
    public string ResetToken { get; set; }

    [Required]
    [DisableAuditing]
    public string Password { get; set; }
}
```

Note: only `ResetToken` and `Password` are required attributes; `UserId` is not annotated `[Required]`
because the empty `Guid` is technically valid, but `UserManager.GetByIdAsync(input.UserId)` will throw
if it doesn't exist.

### `ChangePasswordInput`

```csharp
public class ChangePasswordInput : IValidatableObject
{
    [DisableAuditing]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxPasswordLength))]
    public string CurrentPassword { get; set; }       // optional when the user has no password

    [Required]
    [DisableAuditing]
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxPasswordLength))]
    public string NewPassword { get; set; }

    public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
    {
        if (CurrentPassword == NewPassword)
        {
            var localizer = validationContext.GetRequiredService<IStringLocalizer<AccountResource>>();

            yield return new ValidationResult(
                localizer["NewPasswordSameAsOld"],
                new[] { nameof(CurrentPassword), nameof(NewPassword) }
            );
        }
    }
}
```

The custom `IValidatableObject.Validate` resolves a localizer from the DI scope passed to ABP's
validation infrastructure (see [validation flow](/framework/data-access/abp-validation)) — that's how
the "new password must differ" message gets translated.

`CurrentPassword` is intentionally **not** `[Required]` because the profile service supports the
"first time setting a password" path — `currentUser.PasswordHash == null` calls
`UserManager.AddPasswordAsync` instead of `ChangePasswordAsync`. See
[application](/modules/account/application).

### `ProfileDto`

```csharp
public class ProfileDto : ExtensibleObject, IHasConcurrencyStamp
{
    public string UserName        { get; set; }
    public string Email           { get; set; }
    public string Name            { get; set; }
    public string Surname         { get; set; }
    public string PhoneNumber     { get; set; }
    public bool   IsExternal      { get; set; }
    public bool   HasPassword     { get; set; }
    public string ConcurrencyStamp { get; set; }
}
```

`IHasConcurrencyStamp` triggers ABP's automatic optimistic-concurrency check on the matching
`UpdateProfileDto`. `HasPassword` is the AutoMapper-projected `PasswordHash != null` flag — Blazor and
Razor use it to hide the "current password" input when an external-only user first sets a password.

### `UpdateProfileDto`

```csharp
public class UpdateProfileDto : ExtensibleObject
{
    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxUserNameLength))]
    public string UserName { get; set; }

    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxEmailLength))]
    public string Email { get; set; }

    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxNameLength))]
    public string Name { get; set; }

    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxSurnameLength))]
    public string Surname { get; set; }

    [DynamicStringLength(typeof(IdentityUserConsts), nameof(IdentityUserConsts.MaxPhoneNumberLength))]
    public string PhoneNumber { get; set; }

    public string ConcurrencyStamp { get; set; }
}
```

None of the fields are `[Required]` because the page can be saved partially — the application service
re-reads the user from `UserManager` and only applies fields that actually changed. See
`ProfileAppService.UpdateAsync` in [application](/modules/account/application).

## Settings

```csharp
public class AccountSettingNames
{
    public const string IsSelfRegistrationEnabled = "Abp.Account.IsSelfRegistrationEnabled";
    public const string EnableLocalLogin          = "Abp.Account.EnableLocalLogin";
}
```

`AccountSettingDefinitionProvider` (in the application package) registers both with
`isVisibleToClients: true`, so any UI host can read them through the
application-configuration endpoint or `ISettingProvider`:

```csharp
public override void Define(ISettingDefinitionContext context)
{
    context.Add(
        new SettingDefinition(
            AccountSettingNames.IsSelfRegistrationEnabled,
            "true",
            L("DisplayName:Abp.Account.IsSelfRegistrationEnabled"),
            L("Description:Abp.Account.IsSelfRegistrationEnabled"), isVisibleToClients: true)
    );

    context.Add(
        new SettingDefinition(
            AccountSettingNames.EnableLocalLogin,
            "true",
            L("DisplayName:Abp.Account.EnableLocalLogin"),
            L("Description:Abp.Account.EnableLocalLogin"), isVisibleToClients: true)
    );
}
```

## Localization resource

`AccountResource` lives at `Volo/Abp/Account/Localization/AccountResource.cs`; the JSON files are
embedded under `/Volo/Abp/Account/Localization/Resources/*.json`. Every layer above
(`Application`, `HttpApi`, `Web`, `Blazor`) configures `LocalizationResource = typeof(AccountResource)`
so the `L[...]` indexer resolves the same dictionary.

`Configure<AbpExceptionLocalizationOptions>` maps the `Volo.Account` error-code namespace to this
resource. That's why throwing `new BusinessException("Volo.Account:InvalidEmailAddress", ...)` from the
emailer surfaces a localized message in `Alerts.Danger(...)` on the page.
