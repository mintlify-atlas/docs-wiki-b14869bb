---

`@abp/cms-kit` is a thin **umbrella** package whose only job is to depend on
[`@abp/cms-kit.admin`](/npm/cms-kit-admin) and [`@abp/cms-kit.public`](/npm/cms-kit-public). When you
add `@abp/cms-kit` to a Razor or Blazor host that uses ABP's CMS Kit module, npm + `abp install-libs`
pull in jsTree, slugify, CodeMirror, the TUI editor, Uppy, highlight.js, and star-rating-svg in one
step.

The pack reflects how the CMS Kit module is split server-side. There are two NuGet projects —
`Volo.CmsKit.Admin.Web` (the back-office) and `Volo.CmsKit.Public.Web` (the public-facing widgets) —
and each has its own JS surface. The umbrella package mirrors that split.

## Package metadata

```json
{
    "name": "@abp/cms-kit",
    "version": "7.4.0",
    "license": "LGPL-3.0",
    "dependencies": {
        "@abp/cms-kit.admin":  "~7.4.0",
        "@abp/cms-kit.public": "~7.4.0"
    }
}
```

No JavaScript, no resource mapping. The pack is two lines of `dependencies`.

## Files shipped to the browser

```text
@abp/cms-kit/
├── package.json
└── README.md
```

That's the entire tarball. As with all of ABP's umbrella packs, the visible client-side files come
from:

- The transitive third-party `@abp/<library>` packs (jstree, slugify, codemirror, tui-editor, uppy,
  highlight.js, star-rating-svg) — each shipping an `abp.resourcemapping.js` and being copied into
  `wwwroot/libs/` by `abp install-libs`.
- The **C# projects** `Volo.CmsKit.Admin.Web` and `Volo.CmsKit.Public.Web`, whose own JS lives under
  `src/Volo.CmsKit.{Admin|Public}.Web/Pages/CmsKit/.../*.js` and ships as static web assets.

## What gets pulled in transitively

Through `@abp/cms-kit.admin`:

| Pack               | Why                                                                  |
| ------------------ | -------------------------------------------------------------------- |
| `@abp/codemirror`  | Source-style page/template editor                                    |
| `@abp/jstree`      | The menu items tree in `/CmsKit/Menus/MenuItems`                     |
| `@abp/slugify`     | Auto-slug the blog post URL fragment from the title                  |
| `@abp/tui-editor`  | Markdown WYSIWYG used for `Page` and `BlogPost` editing              |
| `@abp/uppy`        | Multi-file upload widget used by the media manager                   |

Through `@abp/cms-kit.public`:

| Pack                   | Why                                                                |
| ---------------------- | ------------------------------------------------------------------ |
| `@abp/highlight.js`    | Syntax highlighting on rendered blog posts                         |
| `@abp/star-rating-svg` | The five-star widget on the public ratings component               |

All of those packs are catalogued in [`@abp/third-party-packs`](/npm/third-party-packs).

## How a Razor host adopts it

`package.json` of a CMS-enabled host:

```json
{
    "name": "Acme.MyApp.Web",
    "version": "1.0.0",
    "private": true,
    "dependencies": {
        "@abp/aspnetcore.mvc.ui.theme.basic": "~7.4.0",
        "@abp/cms-kit": "~7.4.0"
    }
}
```

Followed by:

```sh
npm install
abp install-libs
```

`wwwroot/libs/` then contains:

```text
wwwroot/libs/
├── jstree/                            ← from @abp/jstree
│   ├── jstree.min.js
│   └── themes/default/...
├── slugify/slugify.js                 ← from @abp/slugify
├── codemirror/codemirror.css / .js    ← from @abp/codemirror
├── tui-editor/tui-editor-full.min.js  ← from @abp/tui-editor
├── uppy/uppy.min.js, uppy.min.css     ← from @abp/uppy
├── highlight.js/highlight.min.js      ← from @abp/highlight.js
└── star-rating-svg/jquery.star-rating-svg.min.js  ← from @abp/star-rating-svg
```

## Razor view example

When you ship the CMS Kit `<Comments />`, `<Reactions />`, or `<Ratings />` view components in your
public pages, the corresponding JS widgets register themselves under `abp.widgets.Cms*` automatically.
From a Razor view:

```html
@page
@model PublicBlogPostModel

<vc:cms-kit-blog-post-render blog-post-id="@Model.BlogPostId" />

<vc:cms-kit-reaction-selection
    entity-type="BlogPost"
    entity-id="@Model.BlogPostId.ToString()" />

<vc:cms-kit-rating
    entity-type="BlogPost"
    entity-id="@Model.BlogPostId.ToString()" />

<vc:cms-kit-commenting
    entity-type="BlogPost"
    entity-id="@Model.BlogPostId.ToString()" />
```

Each view component renders a `<div class="abp-widget-wrapper">` whose data attributes are read by
the corresponding `abp.widgets.Cms*` JS (the actual widget implementations are documented on the
[`@abp/cms-kit.admin`](/npm/cms-kit-admin) and [`@abp/cms-kit.public`](/npm/cms-kit-public) pages).

The widget manager — defined in `@abp/aspnetcore.mvc.ui.theme.shared`'s
[`widget-manager.js`](/npm/aspnetcore-mvc-ui-theme-shared) — wires them up on page load:

```js
new abp.WidgetManager({ wrapper: '#cmsWidgets' }).init();
```

## Gotchas

- **Don't install `@abp/cms-kit` in a Blazor WebAssembly host.** The CMS Kit module's MVC widgets are
  jQuery-based; the WASM host has no jQuery and no `abp.WidgetManager`. The CMS Kit Blazor components
  ship via a different RCL.
- **The pack does not pull in `@abp/aspnetcore.mvc.ui.theme.shared` directly.** That dependency is
  expected to be installed by the host (or via your theme pack). If you list only `@abp/cms-kit` you
  will not have jQuery — the CMS Kit widgets will silently fail.
- **`abp install-libs` is mandatory after every version bump.** Bumping `@abp/cms-kit` from 7.4.0 to
  7.5.0 will not re-copy `jstree.min.js` unless you re-run `abp install-libs`. CMS Kit menus break
  silently if the jstree on disk is older than the C# code that initialises it.
- **There is no JS API directly on `@abp/cms-kit`.** The umbrella exposes neither functions nor
  globals; every widget lives under `abp.widgets.Cms*`, defined in the C# projects' static JS files.
