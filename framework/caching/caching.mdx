`Volo.Abp.Caching` is a thin but opinionated layer sitting **on top of** `Microsoft.Extensions.Caching.Distributed.IDistributedCache`. It does not replace the underlying provider (in-memory, Redis, SQL, etc.) — it *wraps* it so applications can cache **strongly-typed objects** with framework-aware behaviors that the raw `byte[]` API of MS.Extensions.Caching can never offer on its own.

What does that wrapping buy you? Six things, all visible in `DistributedCache<TCacheItem, TCacheKey>`:

1. **Generic typing** — `IDistributedCache<UserCacheItem>` instead of `byte[]`. The module registers an open-generic singleton (`AddSingleton(typeof(IDistributedCache<>), typeof(DistributedCache<>))`) so any `TCacheItem` you reference is resolved automatically; no per-cache DI registration is needed.
2. **Tenant-aware key normalization** — `DistributedCacheKeyNormalizer` prefixes keys with the current tenant id (unless `[IgnoreMultiTenancy]` is on the cache item), making multi-tenant cache isolation automatic and impossible to forget.
3. **A configurable per-cache `DistributedCacheEntryOptions`** — `AbpDistributedCacheOptions.ConfigureCache<TCacheItem>(...)` lets each cache type pick its own sliding/absolute expiration; everything else falls back to `GlobalCacheEntryOptions` (20-minute sliding by default).
4. **JSON serialization via `IDistributedCacheSerializer`** — the default is `Utf8JsonDistributedCacheSerializer` (using `IJsonSerializer`), but you can swap in MessagePack, Protobuf, or BinaryFormatter without rewriting cache call-sites.
5. **Unit-of-work-scoped writes** — when `considerUow: true`, `Set`/`Remove` are buffered in the current `IUnitOfWork` and only flushed to the real cache via `OnCompleted`, so a rolled-back transaction won't poison the cache.
6. **`HideErrors` + `IExceptionNotifier`** — cache misses must never break a request. By default any exception thrown by the underlying provider is swallowed, logged at *Warning*, and forwarded to `IExceptionNotifier`. You can flip `HideErrors = false` (globally or per-call) when you actually want failures to surface.

This page walks through every one of those mechanisms, with source excerpts and a sequence diagram of `GetOrAddAsync`.

## Module wiring

```csharp title="AbpCachingModule.cs"
[DependsOn(
    typeof(AbpThreadingModule),
    typeof(AbpSerializationModule),
    typeof(AbpUnitOfWorkModule),
    typeof(AbpMultiTenancyModule),
    typeof(AbpJsonModule))]
public class AbpCachingModule : AbpModule
{
    public override void ConfigureServices(ServiceConfigurationContext context)
    {
        context.Services.AddMemoryCache();
        context.Services.AddDistributedMemoryCache();

        context.Services.AddSingleton(typeof(IDistributedCache<>), typeof(DistributedCache<>));
        context.Services.AddSingleton(typeof(IDistributedCache<,>), typeof(DistributedCache<,>));

        context.Services.Configure<AbpDistributedCacheOptions>(cacheOptions =>
        {
            cacheOptions.GlobalCacheEntryOptions.SlidingExpiration = TimeSpan.FromMinutes(20);
        });
    }
}
```

Two facts about that snippet matter:

- `AddDistributedMemoryCache()` is called **unconditionally**. So even if you never add a Redis or SQL provider, `IDistributedCache` resolves to an in-process `MemoryDistributedCache`. This makes `IDistributedCache<TCacheItem>` work in unit tests and dev environments out of the box. Adding `Volo.Abp.Caching.StackExchangeRedis` later **replaces** that registration with `AbpRedisCache` via `Services.Replace(...)`.
- The two open-generic singletons mean you can inject `IDistributedCache<MyCacheItem>` directly, with no per-type registration. Resolving `IDistributedCache<X>` makes the container build a `DistributedCache<X>`, which in turn requests `IDistributedCache<X, string>` from the same container — wired by the second `AddSingleton`.

## The contract — two interfaces

### `IDistributedCache<TCacheItem>` — string keys

The 99% case. Use `string` cache keys and let ABP normalize them. The interface extends the keyed one and adds a single property:

```csharp title="IDistributedCache.cs (excerpt)"
public interface IDistributedCache<TCacheItem> : IDistributedCache<TCacheItem, string>
    where TCacheItem : class
{
    IDistributedCache<TCacheItem, string> InternalCache { get; }
}
```

`InternalCache` is occasionally useful — it lets you reach the lower-level keyed cache when you wrote helpers in terms of `IDistributedCache<T, TKey>`.

### `IDistributedCache<TCacheItem, TCacheKey>` — custom keys

Use this when your cache key is *not* a string. Common keys are `Guid` (entity id), `int` (lookup table key), or a small composite record. ABP calls `key.ToString()!` to build the cache key from any `TCacheKey`. The method surface is large but symmetric:

| Method | Description |
| --- | --- |
| `Get` / `GetAsync` | Single read. Returns `null` when the key is missing or — when `hideErrors` — on any provider exception. |
| `GetMany` / `GetManyAsync` | Bulk read. Returns `KeyValuePair<TCacheKey, TCacheItem?>[]` with **exactly** one element per requested key (missing → `Value == null`). |
| `GetOrAdd` / `GetOrAddAsync` | Read-through with a `factory` delegate and an optional `optionsFactory`. Uses a `SemaphoreSlim` to dedupe concurrent factory calls in the same process. |
| `GetOrAddMany` / `GetOrAddManyAsync` | Bulk read-through. Calls the factory once for all missing keys. |
| `Set` / `SetAsync` | Write. Serializes via `IDistributedCacheSerializer`, applies per-cache or global expirations. |
| `SetMany` / `SetManyAsync` | Bulk write. Uses `ICacheSupportsMultipleItems` when available (Redis), otherwise loops. |
| `Refresh` / `RefreshAsync` (+ `Many`) | Resets sliding-expiration timer without re-reading the payload. |
| `Remove` / `RemoveAsync` (+ `Many`) | Eviction. |

Every method takes the same three orthogonal options:

| Parameter | Default | Effect |
| --- | --- | --- |
| `hideErrors` | `null` → falls back to `AbpDistributedCacheOptions.HideErrors` (true) | When true, swallow exceptions and notify `IExceptionNotifier`; when false, rethrow. |
| `considerUow` | `false` | When true, route writes through the current UoW so they flush on commit. |
| `token` (async only) | `default` | Falls back to `ICancellationTokenProvider.Token` if not provided. |

## `CacheItem` and `[CacheName("...")]`

The convention is to define a serializable POCO suffixed `CacheItem`:

```csharp
[Serializable]
public class ProductCacheItem
{
    public string Name { get; set; }
    public decimal Price { get; set; }
}
```

The cache "name" (a logical group, used in key prefixing and per-cache options) is resolved by `CacheNameAttribute.GetCacheName(Type)`:

```csharp title="CacheNameAttribute.cs"
public static string GetCacheName(Type cacheItemType)
{
    var cacheNameAttribute = cacheItemType
        .GetCustomAttributes(true)
        .OfType<CacheNameAttribute>()
        .FirstOrDefault();

    if (cacheNameAttribute != null)
    {
        return cacheNameAttribute.Name;
    }

    return cacheItemType.FullName!.RemovePostFix("CacheItem")!;
}
```

So `ProductCacheItem` (in namespace `Catalog`) becomes the cache name `Catalog.Product`. If you want a shorter or stable name (especially across renames), apply the attribute:

```csharp
[CacheName("Product")]
[Serializable]
public class ProductCacheItem { ... }
```

The cache name shows up in two places:

1. **Key normalization** — the final Redis key looks like `c:<CacheName>,k:<prefix><key>` (see below).
2. **Per-cache options** — `AbpDistributedCacheOptions.ConfigureCache<TCacheItem>(opts)` looks up the cache name to know which configurator to apply.

## Key normalization — tenant isolation by construction

`DistributedCache<TCacheItem, TCacheKey>.NormalizeKey(TCacheKey key)` builds a `DistributedCacheKeyNormalizeArgs` and hands it to the registered `IDistributedCacheKeyNormalizer`:

```csharp title="DistributedCache.cs (excerpt)"
protected virtual string NormalizeKey(TCacheKey key)
{
    return KeyNormalizer.NormalizeKey(
        new DistributedCacheKeyNormalizeArgs(
            key.ToString()!,
            CacheName,
            IgnoreMultiTenancy
        )
    );
}
```

`IgnoreMultiTenancy` is set during `SetDefaultOptions()` by inspecting the cache item type for `[IgnoreMultiTenancy]`:

```csharp
protected virtual void SetDefaultOptions()
{
    CacheName = CacheNameAttribute.GetCacheName(typeof(TCacheItem));
    IgnoreMultiTenancy = typeof(TCacheItem).IsDefined(typeof(IgnoreMultiTenancyAttribute), true);
    DefaultCacheOptions = GetDefaultCacheEntryOptions();
}
```

The default normalizer composes the final key like so:

```csharp title="DistributedCacheKeyNormalizer.cs"
public virtual string NormalizeKey(DistributedCacheKeyNormalizeArgs args)
{
    var normalizedKey = $"c:{args.CacheName},k:{DistributedCacheOptions.KeyPrefix}{args.Key}";

    if (!args.IgnoreMultiTenancy && CurrentTenant.Id.HasValue)
    {
        normalizedKey = $"t:{CurrentTenant.Id.Value},{normalizedKey}";
    }

    return normalizedKey;
}
```

For a multi-tenant request reading `ProductCacheItem` with key `"42"`, in tenant `b3c…`, with `KeyPrefix = "MyApp:"`, the underlying provider sees:

```
t:b3c…,c:Product,k:MyApp:42
```

Properties of this scheme:

- **Tenant isolation is automatic.** Two tenants cannot collide because their normalized keys differ.
- **`[IgnoreMultiTenancy]` opts out** — useful for host-level caches (e.g. tenant resolution itself, where you can't depend on a tenant being known yet).
- **`KeyPrefix`** lets you share one Redis with multiple apps (set it differently per service to avoid collisions).
- The normalizer is `ITransientDependency` and `virtual` — override it if you need a different format.

## `AbpDistributedCacheOptions`

```csharp title="AbpDistributedCacheOptions.cs"
public class AbpDistributedCacheOptions
{
    public bool HideErrors { get; set; } = true;
    public string KeyPrefix { get; set; }
    public DistributedCacheEntryOptions GlobalCacheEntryOptions { get; set; }
    public List<Func<string, DistributedCacheEntryOptions?>> CacheConfigurators { get; set; }

    public void ConfigureCache<TCacheItem>(DistributedCacheEntryOptions? options) { ... }
    public void ConfigureCache(Type cacheItemType, DistributedCacheEntryOptions? options) { ... }
    public void ConfigureCache(string cacheName, DistributedCacheEntryOptions? options) { ... }
}
```

Two configuration styles cooperate:

### Global defaults

```csharp
Configure<AbpDistributedCacheOptions>(opts =>
{
    opts.KeyPrefix = "MyApp:";
    opts.GlobalCacheEntryOptions = new DistributedCacheEntryOptions
    {
        SlidingExpiration = TimeSpan.FromMinutes(10),
        AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
    };
});
```

`AbpCachingModule` itself sets a 20-minute sliding expiration so a freshly created app already has sensible behavior.

### Per-cache overrides

```csharp
Configure<AbpDistributedCacheOptions>(opts =>
{
    opts.ConfigureCache<ProductCacheItem>(new DistributedCacheEntryOptions
    {
        AbsoluteExpiration = DateTimeOffset.Now.AddHours(6)
    });
});
```

Internally that just appends a `Func<string, DistributedCacheEntryOptions?>` to `CacheConfigurators`:

```csharp title="AbpDistributedCacheOptions.cs (excerpt)"
public void ConfigureCache(string cacheName, DistributedCacheEntryOptions? options)
{
    CacheConfigurators.Add(name => cacheName != name ? null : options);
}
```

And `DistributedCache<,>` resolves the right one at startup:

```csharp title="DistributedCache.cs (excerpt)"
protected virtual DistributedCacheEntryOptions GetDefaultCacheEntryOptions()
{
    foreach (var configure in _distributedCacheOption.CacheConfigurators)
    {
        var options = configure.Invoke(CacheName);
        if (options != null)
        {
            return options;
        }
    }
    return _distributedCacheOption.GlobalCacheEntryOptions;
}
```

The first configurator that returns a non-null `DistributedCacheEntryOptions` wins. If none match, the global defaults apply.

You can still override on a *per-call* basis by passing `options` to `Set` / `SetAsync`, or via `optionsFactory` to `GetOrAdd*`.

## Serialization — `IDistributedCacheSerializer`

The default is JSON:

```csharp title="Utf8JsonDistributedCacheSerializer.cs"
public class Utf8JsonDistributedCacheSerializer : IDistributedCacheSerializer, ITransientDependency
{
    protected IJsonSerializer JsonSerializer { get; }

    public byte[] Serialize<T>(T obj)
        => Encoding.UTF8.GetBytes(JsonSerializer.Serialize(obj!));

    public T Deserialize<T>(byte[] bytes)
        => (T)JsonSerializer.Deserialize(typeof(T), Encoding.UTF8.GetString(bytes));
}
```

It piggybacks on `Volo.Abp.Json`'s `IJsonSerializer` so cache items respect the same JSON conventions as your APIs.

Replace it once at startup if you want a faster wire format:

```csharp
context.Services.Replace(
    ServiceDescriptor.Transient<IDistributedCacheSerializer, MyMessagePackSerializer>());
```

Because every serialized payload is just a `byte[]`, the wrapper does not care which serializer you pick.

## Read path — `GetAsync`

```csharp title="DistributedCache.cs (excerpt)"
public virtual async Task<TCacheItem?> GetAsync(
    TCacheKey key,
    bool? hideErrors = null,
    bool considerUow = false,
    CancellationToken token = default)
{
    hideErrors = hideErrors ?? _distributedCacheOption.HideErrors;

    if (ShouldConsiderUow(considerUow))
    {
        var value = GetUnitOfWorkCache().GetOrDefault(key)?.GetUnRemovedValueOrNull();
        if (value != null) return value;
    }

    byte[]? cachedBytes;
    try
    {
        cachedBytes = await Cache.GetAsync(
            NormalizeKey(key),
            CancellationTokenProvider.FallbackToProvider(token));
    }
    catch (Exception ex)
    {
        if (hideErrors == true) { await HandleExceptionAsync(ex); return null; }
        throw;
    }

    if (cachedBytes == null) return null;
    return Serializer.Deserialize<TCacheItem>(cachedBytes);
}
```

Four observations:

1. **UoW-cached writes are seen first.** A `Set(key, val, considerUow: true)` issued earlier in the same UoW will be visible to `Get(considerUow: true)` *before* commit, even though the real cache has not been touched.
2. **Provider exceptions are caught.** The "hide errors" path logs the exception and calls `IExceptionNotifier`; the call returns `null`, indistinguishable from a normal miss.
3. **Cancellation falls back.** If the caller did not pass a token, `ICancellationTokenProvider` fills one in (e.g. a request-aborted token), so a slow Redis call doesn't outlive its request.
4. **Deserialization is delegated** to the registered `IDistributedCacheSerializer` — fully pluggable.

## Bulk reads — `GetMany` and the `ICacheSupportsMultipleItems` capability

`DistributedCache<,>.GetManyAsync` checks whether the underlying `IDistributedCache` also implements `ICacheSupportsMultipleItems`:

```csharp title="DistributedCache.cs (excerpt)"
var cacheSupportsMultipleItems = Cache as ICacheSupportsMultipleItems;
if (cacheSupportsMultipleItems == null)
{
    return await GetManyFallbackAsync(keyArray, hideErrors, considerUow, token);
}
```

- **With Redis** (`AbpRedisCache : RedisCache, ICacheSupportsMultipleItems`) — the call goes through a single pipelined HMGET, returning `byte[]?[]` aligned to the requested keys.
- **Without** the capability (in-memory provider, SQL provider, etc.) — `GetManyFallbackAsync` loops over `GetAsync(key)` calls, one round-trip per item.

In both cases the result schema is identical: `KeyValuePair<TCacheKey, TCacheItem?>[]` with **exactly one** element per requested key (missing keys carry `default(TCacheItem)`).

`SetMany`, `RefreshMany`, `RemoveMany` follow the same pattern: a fast path delegating to `ICacheSupportsMultipleItems` plus a fallback loop. See [caching-redis](caching-redis) for the Redis-side implementation of those batch methods.

## `GetOrAddAsync` — read-through with single-flight semantics

This is the workhorse method. It implements the textbook double-checked-locking idiom over a process-local `SemaphoreSlim`, so two threads in the same process asking for the same missing key only run the factory once:

```csharp title="DistributedCache.cs (excerpt)"
public virtual async Task<TCacheItem?> GetOrAddAsync(
    TCacheKey key,
    Func<Task<TCacheItem>> factory,
    Func<DistributedCacheEntryOptions>? optionsFactory = null,
    bool? hideErrors = null,
    bool considerUow = false,
    CancellationToken token = default)
{
    token = CancellationTokenProvider.FallbackToProvider(token);
    var value = await GetAsync(key, hideErrors, considerUow, token);
    if (value != null) return value;

    using (await SyncSemaphore.LockAsync(token))
    {
        value = await GetAsync(key, hideErrors, considerUow, token);
        if (value != null) return value;

        value = await factory();

        if (ShouldConsiderUow(considerUow))
        {
            var uowCache = GetUnitOfWorkCache();
            if (uowCache.TryGetValue(key, out var item)) item.SetValue(value);
            else uowCache.Add(key, new UnitOfWorkCacheItem<TCacheItem>(value));
        }

        await SetAsync(key, value, optionsFactory?.Invoke(), hideErrors, considerUow, token);
    }

    return value;
}
```

```mermaid
sequenceDiagram
    participant Caller
    participant DC as DistributedCache<T,TKey>
    participant Sem as SyncSemaphore
    participant Norm as KeyNormalizer
    participant Ser as Serializer
    participant Provider as IDistributedCache (Redis/Memory)
    participant Uow as IUnitOfWork

    Caller->>DC: GetOrAddAsync(key, factory)
    DC->>Norm: NormalizeKey(key)
    Norm-->>DC: "t:7,c:Product,k:42"
    DC->>Provider: GetAsync("t:7,c:Product,k:42")
    Provider-->>DC: null (miss)
    DC->>Sem: WaitAsync()
    DC->>Provider: GetAsync(...) (double-check)
    Provider-->>DC: null
    DC->>Caller: await factory()
    Caller-->>DC: new ProductCacheItem
    DC->>Ser: Serialize(item)
    Ser-->>DC: byte[]
    alt considerUow == true && UoW present
        DC->>Uow: stage UnitOfWorkCacheItem; OnCompleted -> SetAsync
        Note over Uow,Provider: write actually flushed at commit
    else
        DC->>Provider: SetAsync(key, byte[], options)
    end
    DC->>Sem: Release
    DC-->>Caller: item
```

A few caveats worth knowing:

- **The semaphore is per-`DistributedCache<,>` instance** — and that instance is a singleton. So the dedupe lock is **per process, per `TCacheItem` type**, not per key. Two distinct keys racing through `GetOrAddAsync` will *serialize* on the semaphore. In practice cache-fill is fast so this is fine, but if your factory is slow, prefer one cache type per logical cache.
- **It is *not* a cross-process lock.** If you need cluster-wide single-flight, layer `IAbpDistributedLock` (see [distributed-locking](distributed-locking)) around the factory.
- The factory's *result* is staged into the UoW dictionary **before** the call to `SetAsync(considerUow: true)` is wired into `OnCompleted`. So even if the UoW rolls back, subsequent reads within the same UoW (e.g. in the catch path) will *still* see the freshly-built item — which is usually what you want.

## Write path — `SetAsync` with UoW staging

```csharp title="DistributedCache.cs (excerpt)"
public virtual async Task SetAsync(
    TCacheKey key, TCacheItem value,
    DistributedCacheEntryOptions? options = null,
    bool? hideErrors = null, bool considerUow = false,
    CancellationToken token = default)
{
    async Task SetRealCache()
    {
        hideErrors = hideErrors ?? _distributedCacheOption.HideErrors;
        try
        {
            await Cache.SetAsync(
                NormalizeKey(key),
                Serializer.Serialize(value),
                options ?? DefaultCacheOptions,
                CancellationTokenProvider.FallbackToProvider(token));
        }
        catch (Exception ex)
        {
            if (hideErrors == true) { await HandleExceptionAsync(ex); return; }
            throw;
        }
    }

    if (ShouldConsiderUow(considerUow))
    {
        var uowCache = GetUnitOfWorkCache();
        if (uowCache.TryGetValue(key, out _))   uowCache[key].SetValue(value);
        else uowCache.Add(key, new UnitOfWorkCacheItem<TCacheItem>(value));

        UnitOfWorkManager.Current?.OnCompleted(SetRealCache);
    }
    else
    {
        await SetRealCache();
    }
}
```

Notice the staging strategy:

- A `UnitOfWorkCacheItem<TCacheItem>` is added to a per-cache, per-UoW dictionary (keyed `"AbpDistributedCache" + CacheName`). That dictionary is fetched via `IUnitOfWork.GetOrAddItem(...)` — so it lives and dies with the UoW.
- `OnCompleted` runs **after** the UoW transaction commits successfully. If the UoW rolls back, `SetRealCache` is never invoked and the cache is untouched.
- Reads done with `considerUow: true` look in this UoW dictionary first — so within the same UoW, *your own* writes are visible immediately even before they hit Redis.

`Remove(considerUow: true)` works the same way: it marks the dictionary entry `IsRemoved = true` (so subsequent reads in the UoW return `null`) and schedules the real `Cache.Remove(...)` for `OnCompleted`.

## UoW staging — `UnitOfWorkCacheItem<T>`

```csharp title="UnitOfWorkCacheItem.cs"
[Serializable]
public class UnitOfWorkCacheItem<TValue> where TValue : class
{
    public bool IsRemoved { get; set; }
    public TValue? Value { get; set; }

    public UnitOfWorkCacheItem<TValue> SetValue(TValue value)
    {
        Value = value; IsRemoved = false; return this;
    }

    public UnitOfWorkCacheItem<TValue> RemoveValue()
    {
        Value = null; IsRemoved = true; return this;
    }
}
```

And the read shortcut:

```csharp title="UnitOfWorkCacheItemExtensions.cs"
public static TValue? GetUnRemovedValueOrNull<TValue>(this UnitOfWorkCacheItem<TValue>? item)
    where TValue : class
{
    return item != null && !item.IsRemoved ? item.Value : null;
}
```

So the staged entry encodes three states: **not present** (`null`), **freshly set** (`Value != null, IsRemoved = false`), **explicitly removed** (`IsRemoved = true`). The read path treats *removed* the same as *absent*, which means a `Remove(considerUow:true)` in the middle of a UoW makes subsequent reads in that UoW see the upcoming deletion immediately.

Use `considerUow: true` whenever the cache value mirrors data you are simultaneously writing through `IRepository`. Otherwise a transaction rollback would leave the cache populated with data that was never persisted.

## Error handling — `HideErrors` and `IExceptionNotifier`

The error policy is "soft by default":

```csharp title="DistributedCache.cs (excerpt)"
protected virtual void HandleException(Exception ex)
{
    _ = HandleExceptionAsync(ex);
}

protected virtual async Task HandleExceptionAsync(Exception ex)
{
    Logger.LogException(ex, LogLevel.Warning);

    using (var scope = ServiceScopeFactory.CreateScope())
    {
        await scope.ServiceProvider
            .GetRequiredService<IExceptionNotifier>()
            .NotifyAsync(new ExceptionNotificationContext(ex, LogLevel.Warning));
    }
}
```

Important details:

- Exceptions never bubble out of the cache when `hideErrors == true` (the default). A Redis blip yields a miss, not a 500.
- Every swallowed exception is **still** observable: the framework logger writes a *Warning*, and `IExceptionNotifier` runs whatever subscribers you have registered (e.g. notification to Sentry, or `IExceptionSubscriber` implementations contributed by other modules).
- A fresh DI scope is created for the notifier so it does not require the calling request to still be active.
- Pass `hideErrors: false` on a specific call (or `Configure<AbpDistributedCacheOptions>(o => o.HideErrors = false)` globally) when you actually want failures to propagate.

## Removal

`Remove`/`RemoveAsync` are mirror images of the set path: with `considerUow: true` they buffer in the UoW (`item.RemoveValue()`) and flush on commit. `RemoveMany` uses `ICacheSupportsMultipleItems.RemoveMany` when available, falling back to a loop otherwise.

```csharp
await _cache.RemoveAsync(productId.ToString(), considerUow: true);
```

If you skip `considerUow` and the surrounding transaction rolls back, you'll have evicted a perfectly valid cache entry — usually harmless, but wasteful.

## `Refresh` — sliding-expiration kick

`Refresh` (and its `Async` / `Many` variants) calls `IDistributedCache.Refresh`, which resets the sliding-expiration timer without re-reading the payload. The Redis provider implements this by issuing the same `EXPIRE` command the lazy refresh path uses internally; the in-memory provider is a no-op.

Use it from background jobs that want to keep "hot" entries warm without re-running their factories.

## Worked example

```csharp
[CacheName("Product")]
[Serializable]
public class ProductCacheItem
{
    public Guid Id { get; set; }
    public string Name { get; set; } = default!;
    public decimal Price { get; set; }
}

public class ProductAppService : ApplicationService
{
    private readonly IDistributedCache<ProductCacheItem, Guid> _cache;
    private readonly IProductRepository _repo;

    public ProductAppService(
        IDistributedCache<ProductCacheItem, Guid> cache,
        IProductRepository repo)
    {
        _cache = cache; _repo = repo;
    }

    public Task<ProductCacheItem?> GetAsync(Guid id) =>
        _cache.GetOrAddAsync(
            id,
            async () =>
            {
                var p = await _repo.GetAsync(id);
                return new ProductCacheItem { Id = p.Id, Name = p.Name, Price = p.Price };
            },
            () => new DistributedCacheEntryOptions
            {
                SlidingExpiration = TimeSpan.FromMinutes(5),
                AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
            });

    public async Task UpdateAsync(Guid id, decimal newPrice)
    {
        var p = await _repo.GetAsync(id);
        p.Price = newPrice;
        await _repo.UpdateAsync(p);

        // Stage eviction so it flushes only if the surrounding transaction commits.
        await _cache.RemoveAsync(id, considerUow: true);
    }
}
```

Or, configure once at startup:

```csharp
Configure<AbpDistributedCacheOptions>(opts =>
{
    opts.KeyPrefix = "MyApp:";
    opts.HideErrors = true;
    opts.ConfigureCache<ProductCacheItem>(new DistributedCacheEntryOptions
    {
        SlidingExpiration = TimeSpan.FromMinutes(5),
        AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
    });
});
```

…and skip the `optionsFactory` everywhere.

## Customization hooks

| Hook | How |
| --- | --- |
| Replace the underlying provider | Register a different `IDistributedCache` (`AddStackExchangeRedisCache`, `AddDistributedSqlServerCache`, …). The wrapper does not care. |
| Change the key scheme | Implement `IDistributedCacheKeyNormalizer` and `Services.Replace(...)` the default. |
| Change serialization | Implement `IDistributedCacheSerializer`. The default is JSON. |
| Per-cache options | `opts.ConfigureCache<TCacheItem>(new DistributedCacheEntryOptions { ... })`. |
| Per-call options | Pass `options` to `Set`/`SetAsync` or `optionsFactory` to `GetOrAdd*`. |
| Disable error hiding | `Configure<AbpDistributedCacheOptions>(o => o.HideErrors = false)` or per-call `hideErrors: false`. |
| Specialize a particular cache | Derive `MyCache : DistributedCache<TItem, TKey>` and register it; everything is `virtual`. |
