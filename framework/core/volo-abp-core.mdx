`Volo.Abp.Core` is the package that physically contains the ABP kernel.
It targets `netstandard2.0`, `netstandard2.1`, and `net7.0`, and exposes
everything that user code touches under the `Volo.Abp.*` namespace — the
application host, the module system, dependency injection conventions,
exception handling, dynamic proxy abstractions, simple state checkers,
reflection helpers, threading primitives, and a small set of `Volo.Abp`
root types such as `BusinessException`, `Check`, and `IRemoteService`.

The csproj does not depend on any other ABP package. It only references
Microsoft.Extensions packages (DI, Configuration, Localization,
Logging, Hosting.Abstractions, Options), `JetBrains.Annotations`, and
`Nito.AsyncEx.*`. That self‑contained nature is what lets it act as the
substrate every other framework package builds on.

Key observations:

- **`Nullable` is enabled** with `Nullable` warnings treated as errors,
  so every public API in the kernel has explicit nullable annotations.
- **`System.Runtime.Loader`** is pulled in for `AssemblyLoadContext`,
  used by `FilePlugInSource` and `FolderPlugInSource`.
- **`Nito.AsyncEx.Coordination`** supplies `AsyncLock` and similar
  primitives used by ABP threading helpers.
- The reference set is intentionally small: no JSON serializer, no MVC,
  no Entity Framework. The kernel cannot bootstrap a web app on its own,
  but anything in `Microsoft.Extensions.*` is already available.

The `Microsoft/Extensions/...` tree contains extension methods ABP
contributes to Microsoft's own namespaces (so users can call
`IServiceCollection.AddApplication<TModule>()` without an extra
`using`). The `Volo/Abp/...` tree is the home for everything ABP
authors.

The `Microsoft/Extensions/Configuration/ConfigurationHelper.cs` file is
worth a direct look because it is what `AbpApplicationBase` falls back
to when no `IConfiguration` is registered:

```csharp framework/src/Volo.Abp.Core/Microsoft/Extensions/Configuration/ConfigurationHelper.cs
public static IConfigurationRoot BuildConfiguration(
    AbpConfigurationBuilderOptions? options = null,
    Action<IConfigurationBuilder>? builderAction = null)
{
    options ??= new AbpConfigurationBuilderOptions();

    if (options.BasePath.IsNullOrEmpty())
    {
        options.BasePath = Directory.GetCurrentDirectory();
    }

    var builder = new ConfigurationBuilder()
        .SetBasePath(options.BasePath!)
        .AddJsonFile(options.FileName + ".json", optional: options.Optional, reloadOnChange: options.ReloadOnChange);

    if (!options.EnvironmentName.IsNullOrEmpty())
    {
        builder = builder.AddJsonFile($"{options.FileName}.{options.EnvironmentName}.json", optional: options.Optional, reloadOnChange: options.ReloadOnChange);
    }

    if (options.EnvironmentName == "Development")
    {
        if (options.UserSecretsId != null)
        {
            builder.AddUserSecrets(options.UserSecretsId);
        }
        else if (options.UserSecretsAssembly != null)
        {
            builder.AddUserSecrets(options.UserSecretsAssembly, true);
        }
    }

    builder = builder.AddEnvironmentVariables(options.EnvironmentVariablesPrefix);

    if (options.CommandLineArgs != null)
    {
        builder = builder.AddCommandLine(options.CommandLineArgs);
    }

    builderAction?.Invoke(builder);

    return builder.Build();
}
```

## How the kernel bootstraps itself

Two `internal` static methods in `Volo.Abp.Internal.InternalServiceCollectionExtensions`
wire everything together. `AbpApplicationBase` calls them in its
constructor:

```csharp framework/src/Volo.Abp.Core/Volo/Abp/Internal/InternalServiceCollectionExtensions.cs
internal static void AddCoreServices(this IServiceCollection services)
{
    services.AddOptions();
    services.AddLogging();
    services.AddLocalization();
}

internal static void AddCoreAbpServices(this IServiceCollection services,
    IAbpApplication abpApplication,
    AbpApplicationCreationOptions applicationCreationOptions)
{
    var moduleLoader = new ModuleLoader();
    var assemblyFinder = new AssemblyFinder(abpApplication);
    var typeFinder = new TypeFinder(assemblyFinder);

    if (!services.IsAdded<IConfiguration>())
    {
        services.ReplaceConfiguration(
            ConfigurationHelper.BuildConfiguration(
                applicationCreationOptions.Configuration
            )
        );
    }

    services.TryAddSingleton<IModuleLoader>(moduleLoader);
    services.TryAddSingleton<IAssemblyFinder>(assemblyFinder);
    services.TryAddSingleton<ITypeFinder>(typeFinder);
    services.TryAddSingleton<IInitLoggerFactory>(new DefaultInitLoggerFactory());

    services.AddAssemblyOf<IAbpApplication>();

    services.AddTransient(typeof(ISimpleStateCheckerManager<>), typeof(SimpleStateCheckerManager<>));

    services.Configure<AbpModuleLifecycleOptions>(options =>
    {
        options.Contributors.Add<OnPreApplicationInitializationModuleLifecycleContributor>();
        options.Contributors.Add<OnApplicationInitializationModuleLifecycleContributor>();
        options.Contributors.Add<OnPostApplicationInitializationModuleLifecycleContributor>();
        options.Contributors.Add<OnApplicationShutdownModuleLifecycleContributor>();
    });
}
```

That single block tells you the entire kernel story:

1. Microsoft.Extensions options/logging/localization are turned on.
2. A configuration root is built from `AbpConfigurationBuilderOptions`
   if the caller did not already register one.
3. The module loader, assembly finder, type finder, and init‑logger
   factory are registered as singletons.
4. The kernel's own assembly is added through the conventional
   registrar so types like `ExceptionNotifier`, `CachedServiceProvider`
   and `AbpLazyServiceProvider` get registered automatically.
5. `ISimpleStateCheckerManager<>` is registered.
6. Four `IModuleLifecycleContributor` types are registered into
   `AbpModuleLifecycleOptions.Contributors` to power
   `OnPreApplicationInitialization`, `OnApplicationInitialization`,
   `OnPostApplicationInitialization`, and `OnApplicationShutdown`.

No other ABP package needs to be installed for the host to come up.

## Take‑aways

- `Volo.Abp.Core` is self‑contained; its only dependencies are
  Microsoft.Extensions packages and a handful of utility libraries.
- Root types under `Volo/Abp/` are domain‑neutral primitives every
  module reuses: exceptions, guards, host info, lifecycle contexts.
- Every subnamespace has a focused job; the rest of this section walks
  the most important ones in depth.
